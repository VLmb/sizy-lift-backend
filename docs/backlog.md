# Бэклог сервера

Задачи, которые решено сделать позже. Порядок — примерный приоритет внутри раздела.

## Наблюдаемость (развитие [observability.md](observability.md))

- **Дашборды Grafana как код** (provisioning из репозитория, а не руками в UI):
  - JVM и Spring: HTTP-запросы и задержки по эндпоинтам, ошибки 4xx/5xx, память, GC, Hikari;
  - публикация: пачки в минуту, принятые / устаревшие / отклонённые элементы по типам, время пачки;
  - «Обзор Sizy»: число аккаунтов, новые регистрации, объём опубликованных данных —
    SQL-панели по PostgreSQL через отдельного пользователя только на чтение.
- **Вход в Grafana через Keycloak** (OIDC, доступ только с ролью администратора) вместо пароля
  `admin`; туннель можно оставить как второй рубеж.
- **Метрики инфраструктуры:** Keycloak (`KC_METRICS_ENABLED`, входы и ошибки входа),
  PostgreSQL (`postgres_exporter`), Caddy.
- **Трейсы JDBC:** span на SQL-запросы (datasource-micrometer), чтобы видеть медленные запросы
  в трейсе публикации.
- **Алерты:** бэкенд недоступен, рост 5xx, отклонённые публикации, заканчивается диск.
- **Хранение:** сроки хранения метрик, логов и трейсов; при росте нагрузки — отдельные
  контейнеры коллектора, Prometheus/Mimir, Tempo, Loki вместо `otel-lgtm`; sampling трейсов
  ниже 1.0 (`TRACING_SAMPLING_PROBABILITY`).

## Вход и аккаунты

- **Мгновенный отзыв access JWT при logout** (добавлено 27.10.2026).
  Сейчас API проверяет JWT локально: после выхода токен действует до exp с допуском времени
  (TTL 5 минут, допуск 60 секунд). Выбрать проверку активности в Keycloak либо общий список
  отозванных сессий с ограниченным сроком хранения; определить выход из текущей и всех сессий.
  Сохранить API без HttpSession и cookie-авторизации. Предусмотреть проверенные события logout
  Keycloak, очистку состояния открытых вкладок и поведение при недоступности хранилища отзывов.
  Критерии: скопированный access token после подтверждённого logout получает 401, refresh не
  восстанавливает завершённую сессию, выход с одного устройства не завершает другие без явного
  выбора. Проверить гонки logout/refresh и несколько экземпляров backend. Контекст —
  [authentication.md](authentication.md#проверка-границ-веба-26-октября-2026).
- **Своя тема Keycloak в стиле Sizy** (`keycloak/themes/sizy`, поверх стандартной `keycloak.v2`): вход,
  регистрация, «Забыли пароль?», подтверждение почты, ошибки — тёмный фон, оранжевый акцент, шрифт DIN,
  логотип, короткие тексты на русском. Письма (подтверждение почты, сброс пароля) — своя email-тема в том же
  стиле. Логику Keycloak не трогаем; страницы общие для веба и мобильного приложения. Сначала HTML-макеты на
  согласование. Тема копируется в образ Keycloak, в realm — `loginTheme` и `emailTheme`; на уже созданном
  realm в production тему один раз выбрать в админке (Realm settings → Themes).
- **Вход через Google и Meta (Facebook).** Провайдеры уже описаны в realm и выключены
  (`GOOGLE_IDP_ENABLED`, `FACEBOOK_IDP_ENABLED`). Нужно: приложения в Google Cloud Console и Meta for
  Developers, redirect URI `https://<AUTH_DOMAIN>/realms/sizylift/broker/{google|facebook}/endpoint`, ключи в
  `deploy/.env` и включение в админке (на созданном realm переменные уже не применяются); кнопки на странице
  входа (вместе с темой); проверка привязки к существующему аккаунту с той же почтой и входа из мобильного
  приложения. У Meta — проверка приложения и политика конфиденциальности на домене.

## Для sizy-lift-app (добавлено 28.10.2026)

Задачи приложения по итогам решений о классе упражнения и %ПМ; подробности —
[coach-workspace.md](coach-workspace.md), раздел 6. Сервер держит совместимость через `isSbd`.

- Проверить механику ПМ в приложении (e1RM, рекорды, графики) с классами `sbd` / `basic` / `other`.
- Синхронизировать приложение с новой схемой сервера: `lift_class` вместо `is_sbd`, разметка каталога, `liftClass`
  в публикации и ленте, общие фикстуры.
- Создание нового упражнения: обязательный явный выбор класса с пояснением.
- После перехода приложения — убрать `isSbd` из контракта сервера.

## Сборка и развёртывание

- **Разобраться с CI/CD backend и frontend** (добавлено 30.10.2026).
  Проверить текущие GitHub Actions и ручной процесс обновления сервера. Определить,
  как запускать проверки, собирать JAR и Docker-образы в CI и доставлять готовые версии
  на сервер без ручной сборки. Продумать согласованный выпуск backend/frontend,
  хранение секретов, проверку работоспособности после обновления, откат и очистку
  старых образов/кеша с учётом ограниченного SSD. Результат — понятная схема и план
  внедрения с выбором ручного подтверждения или автоматического запуска деплоя.
