# ADR-0007: Синхронизация в обе стороны и данные тренера

Статус: предложено
Дата: 23 октября 2026
Основание: [ADR-0006 «Тренер и подопечный»](https://github.com/VLmb/sizy-lift-app/blob/main/docs/architecture/adr/0006-coach-and-athlete.md)
(функциональное описание), текущая публикация — [publication.md](../publication.md).

## Контекст

Сейчас данные текут в одну сторону. Телефон публикует агрегаты (тренировка, программа,
упражнение, профиль, 1ПМ, травма, противопоказание) пачками, сервер хранит реляционную копию.
Повторы и перестановки безопасны благодаря монотонной версии агрегата, которую ведёт сам
телефон (`published_aggregate.version`).

ADR-0006 добавляет:

1. **Данные, которые пишет не владелец.** Тренер пишет программы подопечного, подопечный
   переносит тренировки тренера, оба пишут комментарии.
2. **Второе место правки своих данных** — веб-версию. Одну программу можно поправить
   на телефоне и в браузере.
3. **Чтение чужих данных.** Тренер видит тренировки подопечного, с разрешения — травмы.
   Фото тренер не видит.
4. **Доставку на телефон**, в том числе офлайн-копию данных подопечных у тренера.

Версия, которую ведёт один телефон, для этого не годится. Версии двух писателей несравнимы,
а у сервера нет способа сказать телефону «вот что изменилось».

## Решение коротко

- **Стек не меняется:** Java 25, Spring Boot 4.1, PostgreSQL 18, Liquibase, `JdbcTemplate`,
  Keycloak. Ни брокера сообщений, ни второй базы, ни WebSocket.
- **Источник истины для общих данных — сервер.** Каждая запись агрегата получает серверную
  ревизию.
- **Запись — оптимистичная, с базовой ревизией.** Конфликт решается правилом «побеждает
  последнее изменение» (решение владельца). Проигравшая версия сохраняется в журнале.
- **Чтение на телефон — через персональную ленту изменений** с курсором. Push — только
  сигнал «загляни в ленту».
- **Права проверяются в одном месте**, `AccessPolicy`, и во всех запросах выражаются
  фильтром по владельцу.

## 2. Владелец, автор и ревизия агрегата

Метаданные агрегата живут в существующей таблице `published_aggregate`. Её смысл расширяется
до «состояния агрегата на сервере».

```sql
-- новый changeset; существующие колонки остаются
ALTER TABLE sizylift.published_aggregate
    ADD COLUMN revision          bigint      NOT NULL DEFAULT 0, -- серверная ревизия, растёт при каждой записи
    ADD COLUMN changed_at        timestamptz,                    -- когда автор сделал изменение (часы клиента, см. 3)
    ADD COLUMN author_user_id    uuid,                           -- кто имеет право писать (NULL = владелец)
    ADD COLUMN source_client_id  text,                           -- устройство или веб-сессия последней записи
    ADD COLUMN source_version    bigint;                         -- локальная версия на этом клиенте (идемпотентность)
CREATE SEQUENCE sizylift.aggregate_revision_seq;
```

- **Владелец** (`user_id`, уже в ключе) — чьи это данные. Программу тренера для подопечного
  хранят под `user_id` подопечного: так тренировки ссылаются на неё как раньше, а подопечный
  видит её как свою.
- **Автор** (`author_user_id`) — единственный, кто может писать агрегат. `NULL` значит
  «пишет владелец». Обычная запись автора не меняет: его ставит только создание программы
  тренером и передача программ подопечному при разрыве (раздел 5). Для программы тренера это тренер. Правило «один писатель» из ADR-0006
  проверяется здесь, а не на клиенте.
- **Ревизия** — значение из общей последовательности, назначается при каждой записи. Нужна
  только монотонность внутри агрегата; общая последовательность проще отдельного счётчика.
- Новые типы агрегатов: `workout_reschedule` (перенос, пишет подопечный) и `workout_comment`
  (комментарий, пишет его автор). Они получают ту же механику записи, ленты и прав.

## 3. Запись: базовая ревизия и «побеждает последнее»

Новый эндпоинт `POST /api/v2/sync/push` — развитие `publication/batch` с тем же форматом пачки
и payload, но с новыми полями элемента:

```json
{ "type": "program", "id": "…", "ownerId": "…",          // ownerId — только когда пишем чужое (тренер)
  "baseRevision": 41,                                     // ревизия, от которой клиент правил; 0 — новый
  "changedAt": "2026-10-23T09:14:02Z",                    // время последней локальной правки
  "clientId": "device-7f3a…", "clientVersion": 18,         // идемпотентность повтора
  "deleted": false, "schemaVersion": 1, "payload": { … } }
```

Обработка одного элемента — своя транзакция, как сейчас:

1. **Право записи.** `AccessPolicy.canWrite(caller, owner, type, author)`: сам владелец
   без чужого автора; тренер для своих программ у активного подопечного; автор комментария.
   Иначе `rejected: forbidden`.
2. **Блокировка состояния агрегата** — `INSERT … ON CONFLICT DO NOTHING` +
   `SELECT … FOR UPDATE`, как сейчас в `lockVersion`. Параллельные записи одного агрегата
   выстраиваются в очередь.
3. **Повтор той же правки** (`clientVersion` ≤ последней обработанной от этого `clientId` по
   агрегату) → `stale` с текущей ревизией. Это прежняя идемпотентность, теперь по клиенту, а не по
   агрегату. Версия хранится по каждому клиенту отдельно (`aggregate_client_version(user_id, type,
   aggregate_id, client_id, version)`, upsert при обработке), а не только у последнего писателя:
   иначе повтор правки, ответ на которую потерялся, после записи другого клиента пошёл бы как
   конфликт и мог бы откатить более позднюю чужую правку.
4. **Перемотка вперёд** (`baseRevision` = текущей ревизии) → записать, новая ревизия, `accepted`.
5. **Конфликт** (`baseRevision` ≠ текущей). Обычно база меньше: кто-то записал после того, как
   клиент прочитал. База больше текущей у корректного клиента невозможна (бывает после
   восстановления базы из бэкапа); такую правку тоже решаем как конфликт и считаем метрикой,
   чтобы правки телефонов не побеждали молча:
   - сравнить `changedAt` входящей правки и сохранённой;
   - входящая новее → записать её, а сохранённую версию положить в `aggregate_conflict`;
     ответ `accepted`;
   - входящая старше или равна → не записывать, положить её в `aggregate_conflict`;
     ответ `superseded` с текущей ревизией. Клиент перечитает агрегат из ленты и покажет:
     «Ваши правки от 10:00 заменены более поздними из веба (12:00)».
6. **Фан-аут в ленты** (раздел 4) — в той же транзакции.

**Почему время правки, а не время прихода.** «Последнее изменение» пользователь понимает
как сделанное позже, а не дошедшее позже. Телефон, поправленный офлайн в 10:00, не должен
затереть правку из веба в 12:00 только потому, что поймал сеть в 15:00.

**Часы клиента.** `changedAt` обрезается до `min(changedAt, now() сервера)`: правка из
будущего не выигрывает вечно. Ничья решается в пользу уже сохранённой версии — она детерминирована.

**Журнал конфликтов** `aggregate_conflict(user_id, type, aggregate_id, lost_payload jsonb,
lost_changed_at, lost_client_id, winner_revision, created_at)` хранится 30 дней. Вытесненная
сохранённая версия собирается в payload `AggregateReader` (раздел 4) до замены; пуст `lost_payload`
только у tombstone. Восстановление
из него в интерфейсе — позже. Данные не пропадают молча.

**Совместимость со старым приложением.** `publication/batch` (v1) остаётся, пока приложение
не обновится. Его элемент трактуется как запись владельца с неизвестной базой: конфликт
решается по `updatedAt` корня payload. Это поле в v1 уже есть. Уточнение: счётчик `version` остаётся
первым барьером (`stale`, как раньше); сравнение по `updatedAt` включается, только если агрегат
последним записан через v2, поэтому порядок записей чисто-v1 клиента не меняется. У v1 нет статуса
`superseded`, проигравшая запись получает `stale` и попадает в журнал; у tombstone v1 времени правки
нет, берётся время получения. С этапа 3 v1 отклоняет запись агрегата, у которого `author_user_id`
задан и не равен владельцу: старое приложение подопечного не знает авторов и иначе опубликовало бы
свою копию программы тренера, тихо забрав её себе.

**Удаление** — запись с `deleted = true` по тем же правилам: tombstone с ревизией. Удаление
и правка конкурируют по `changedAt`, как две правки.

## 4. Чтение на телефон: персональная лента изменений

### Модель

```sql
CREATE TABLE sizylift.sync_cursor (
    user_id  uuid   PRIMARY KEY REFERENCES sizylift.user_account (id) ON DELETE CASCADE,
    last_seq bigint NOT NULL DEFAULT 0
);
CREATE TABLE sizylift.sync_feed (
    user_id       uuid   NOT NULL,      -- получатель
    seq           bigint NOT NULL,      -- позиция в ленте получателя
    owner_user_id uuid   NOT NULL,      -- чьи данные
    type          text   NOT NULL,
    aggregate_id  uuid   NOT NULL,
    revision      bigint NOT NULL,
    kind          text   NOT NULL CHECK (kind IN ('upsert', 'delete', 'revoke')),
    PRIMARY KEY (user_id, seq),
    UNIQUE (user_id, owner_user_id, type, aggregate_id)
);
```

### Почему не общая последовательность

Наивный курсор «все записи с `revision > N`» теряет данные. Значения последовательности
выдаются при вставке, а видны после коммита, и коммиты идут не по порядку. Транзакция
с ревизией 101 может закоммититься раньше транзакции с ревизией 100. Клиент прочитает 101,
сдвинет курсор и навсегда пропустит 100.

Поэтому позиция в ленте выдаётся **под блокировкой строки `sync_cursor` получателя**
(`UPDATE sync_cursor SET last_seq = last_seq + 1 WHERE user_id = ? RETURNING last_seq`).
Записи в ленту одного получателя сериализуются, и порядок `seq` совпадает с порядком коммитов.
Конкуренция есть только за ленту одного человека: это его устройства и его тренер, единицы
записей в секунду.

**Взаимные блокировки.** Одна запись добавляется в несколько лент: владельца и тренера.
Строки `sync_cursor` всегда блокируются в порядке `user_id` и всегда последними в транзакции,
после блокировки агрегата и записи данных. Двух записей, которые ждут друг друга по кругу,
не возникает. Блокировка курсора держится только до коммита, то есть миллисекунды.

### Лента — индекс последних изменений, а не журнал

`UNIQUE (user_id, owner_user_id, type, aggregate_id)`: при новой записи агрегата строка ленты
не добавляется, а переезжает на новый `seq` (`INSERT … ON CONFLICT … DO UPDATE SET seq = …`).
Отсюда три следствия:

- размер ленты = числу видимых агрегатов, она не растёт бесконечно, очистка по сроку не нужна;
- клиент, долго бывший офлайн, получает только последнее состояние каждого агрегата;
- полная пересинхронизация — то же чтение с `after=0`.

### Кому что попадает в ленту (фан-аут)

| Изменение                                 | Ленты получателей                                                   |
| ----------------------------------------- | ------------------------------------------------------------------- |
| любой агрегат владельца                   | владелец (его другие устройства и веб)                              |
| тренировка, программа, профиль, 1ПМ, своё упражнение подопечного | + тренер с активной связью                    |
| травма, противопоказание подопечного      | + тренер, только если `health_access = true`                        |
| программа тренера, перенос, комментарий   | подопечный и тренер                                                 |
| связь создана / включён `health_access`   | тренеру — разовое добавление всех видимых агрегатов подопечного     |
| связь разорвана / выключен `health_access` | тренеру — `revoke` по каждому агрегату; телефон удаляет копию      |

Фото не публикуются вовсе (`docs/publication.md`), поэтому тренеру их нечего отдавать.
Это закреплено тестом.

### API

`GET /api/v2/sync/changes?after=<seq>&limit=<n>` возвращает до `n` записей ленты по
возрастанию `seq`, сразу с актуальным payload агрегата, и `nextCursor`. Payload собирается
из реляционных таблиц читателем агрегата (`AggregateReader` — зеркало существующих
`AggregatePublisher`) в том же формате v1, что и при публикации. Телефону не нужен второй
формат. Размер страницы ограничен и числом записей, и объёмом. Страница ленты и payload читаются
из одного снимка (`REPEATABLE READ`), чтобы ревизия записи совпадала с отданными данными. Ответ
дополнительно несёт `changedAt` агрегата (для сообщения «ваши правки заменены») и `hasMore`.

Записи v1 тоже попадают в ленту: обе точки записи вызывают `AggregateChangeListener` последним
шагом транзакции, фан-аут реализован в `sync`. Так `publication` не зависит от `sync`.

### Что должен соблюдать клиент

- Сохранять `revision` агрегата и отправлять её как `baseRevision` при следующей правке.
- **Не публиковать обратно полученное.** Применять агрегат из ленты, не поднимая локальную
  версию и не ставя его в outbox (в приложении это триггеры публикации). Иначе получится
  бесконечный пинг-понг.
- Пропускать собственное эхо: запись ленты с `revision`, равной уже сохранённой, — ничего
  не делать.
- Сдвигать курсор только после локального коммита страницы.

Детали — в ADR приложения.

## 5. Связь тренера и подопечного

```sql
CREATE TABLE sizylift.coaching_invite (
    id            uuid        PRIMARY KEY,
    coach_user_id uuid        NOT NULL REFERENCES sizylift.user_account (id) ON DELETE CASCADE,
    token_hash    bytea       NOT NULL UNIQUE,          -- SHA-256 от токена; сам токен не хранится
    created_at    timestamptz NOT NULL DEFAULT now(),
    expires_at    timestamptz NOT NULL,                 -- 7 дней
    accepted_at   timestamptz,
    accepted_by   uuid
);
CREATE TABLE sizylift.coaching_link (
    id              uuid        PRIMARY KEY,
    coach_user_id   uuid        NOT NULL REFERENCES sizylift.user_account (id) ON DELETE CASCADE,
    athlete_user_id uuid        NOT NULL REFERENCES sizylift.user_account (id) ON DELETE CASCADE,
    health_access   boolean     NOT NULL DEFAULT false,
    created_at      timestamptz NOT NULL DEFAULT now(),
    ended_at        timestamptz
);
-- у подопечного один активный тренер
CREATE UNIQUE INDEX coaching_link_active_athlete ON sizylift.coaching_link (athlete_user_id) WHERE ended_at IS NULL;
```

- **Приглашение** — случайный токен из 128 бит в ссылке `https://<домен>/invite/<token>`
  (universal link / app link открывает приложение). В базе хранится только хеш: утечка базы
  не даёт рабочих ссылок. Ссылка одноразовая и живёт 7 дней.
- **Принятие** — `POST /api/v2/coaching/invites/{token}/accept`. В одной транзакции: создать
  связь, засеять ленту тренера (раздел 4), поставить уведомление тренеру (ADR-0009).
- **Разрыв** любой стороной: `ended_at`, `revoke` в ленту тренера. Программы тренера
  переходят подопечному: `author_user_id = NULL`, новая ревизия, запись в ленту подопечного.
  Так подопечный получает их как свои редактируемые.
- **Режим тренера** — флаг `user_account.coach_enabled`. Лимит подопечных не вводим, оплата
  отложена.
- **Предпросмотр** `GET /api/v2/coaching/invites/{token}`: кто приглашает и какие данные увидит тренер —
  ADR-0006 требует показать это до принятия.
- **Сериализация со записью данных.** Изменение связи (принятие, `health_access`, разрыв) берёт
  исключительную блокировку аккаунта подопечного, запись его данных — разделяемую, первым шагом
  транзакции. Общий порядок блокировок: аккаунт владельца → агрегат → курсоры лент. Иначе запись,
  посчитавшая тренера получателем до разрыва, дописала бы ему данные после `revoke`. Засев и `revoke`
  резервируют диапазон позиций под той же блокировкой курсора.
- Уведомление тренеру о принятии ставится в этапе 5 (ADR-0009), когда появится `notification_outbox`.
- **Упражнения тренера в программе подопечного.** Id упражнения на сервере уникален глобально, поэтому
  при записи тренером программы сервер копирует его собственные упражнения в библиотеку подопечного
  под производным постоянным id и переписывает ссылки программы на копии (ответ
  `payloadRewritten: true`). Копия — упражнение подопечного: он её правит, она остаётся после разрыва
  и после удаления исходного упражнения тренером. Существующую копию сервер не перезаписывает.
  Отклонено: общий доступ к упражнению тренера (пропало бы при удалении тренером и продолжало бы
  получать его правки после разрыва) и ключ `(user_id, id)` у `exercise` (меняет общую с каталогом
  схему и FK упражнений).

## 6. Права доступа: `AccessPolicy`

Одна служба отвечает на два вопроса:

- `canWrite(caller, owner, type, author)` — правила из раздела 3;
- `readableOwners(caller, type)` — чьи данные этого типа видит caller: он сам плюс активные
  подопечные. Для травм и противопоказаний — только с `health_access`.

Все запросы чтения получают список владельцев из `readableOwners` и фильтруют
`WHERE user_id = ANY(?)`. Контроллер никогда не принимает чужой `user_id` без этой проверки.
Лента читается по получателю, поэтому каждая запись о чужих данных перепроверяется `canRead`: без права
вместо payload отдаётся `revoke`. «403 после разрыва» в batch-API выражается построчно: запись тренера
получает `rejected: forbidden`; операции со связью, которые сторона делать не может, — HTTP `403`.
Тест-матрица «роль × тип агрегата × состояние связи × health_access» проверяет и запись,
и чтение, и фан-аут.

## 7. Перенос тренировки

Отдельный агрегат `workout_reschedule(user_id = подопечный, planned_workout_id, program_id,
scheduled_date, changed_at)`. Его пишет подопечный, а саму программу не трогает. Каждую
строку пишет ровно один автор.

- Календарь показывает дату переноса, если она есть, иначе дату из программы.
- Если тренер потом сам меняет дату этой плановой тренировки, сервер удаляет перенос
  в той же транзакции, сравнивая старую и новую дату при замене программы. Действует
  последнее изменение, как и везде.
- Если плановая тренировка удалена, перенос удаляется вместе с ней.

## 8. Комментарии

Агрегат `workout_comment(user_id = автор, id, workout_owner_id, workout_id, text, created_at,
deleted)`. Правит и удаляет только автор. В ленту попадает автору и второй стороне связи,
второй стороне ставится уведомление. Текст в логи не пишется.

## 9. Миграции

Новые changeset'ы, существующие не меняются:

1. колонки `published_aggregate` + `aggregate_revision_seq`;
2. заполнение для уже опубликованного: `revision = nextval`, `changed_at` из `updated_at`
   корня, `author_user_id = NULL`;
3. `sync_cursor`, `sync_feed` и засев лент владельцев всеми их агрегатами, чтобы первое
   чтение с `after=0` вернуло всё;
4. `coaching_invite`, `coaching_link`, `user_account.coach_enabled`;
5. `workout_reschedule`, `workout_comment`, `aggregate_conflict`, расширение CHECK по `type`.

Засев идёт одним `INSERT … SELECT` в changeset. При текущем объёме данных это секунды.

## 10. Проверки

- Интеграционные тесты на Testcontainers PostgreSQL, как сейчас.
- **Конкурентность:** N потоков пишут агрегаты одного владельца. Читатель, который параллельно
  ходит по ленте курсором, видит каждую последнюю ревизию ровно один раз и ничего не пропускает.
- **Конфликты:** база устарела, правка новее → `accepted`; правка старше → `superseded`;
  в журнале проигравший payload.
- **Матрица прав** (раздел 6), включая «тренер не видит травмы без разрешения» и «после
  разрыва — `revoke` и 403».
- Метрики: `sizylift.sync.push.items{type,status}`, `sizylift.sync.changes.page.size`,
  `sizylift.sync.conflicts{type,outcome}`, `sizylift.sync.push.base.ahead{type}`.

## Рассмотрено и отклонено

- **Kafka / RabbitMQ / Debezium** для доставки. Добавили бы эксплуатацию. Лента в PostgreSQL
  с блокировкой курсора даёт ту же гарантию порядка.
- **Глобальная последовательность или `xmin` как курсор.** Пропуски при коммитах не по порядку
  (раздел 4) или зависимость от внутренностей PostgreSQL.
- **Слияние на уровне полей / CRDT.** Сложно, непрозрачно, владелец выбрал last-writer-wins.
- **Блокировка программы на время правки в вебе.** Владелец выбрал «побеждает последнее».
- **WebSocket / SSE для телефона.** Не живут в фоне; push-сигнал + pull проще и надёжнее.
- **Firebase / Supabase как готовая синхронизация.** Второй источник истины рядом с
  PostgreSQL и Keycloak, и привязка к внешнему сервису.
