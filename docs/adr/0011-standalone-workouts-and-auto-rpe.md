# ADR-0011: Разовые тренировки в синхронизации, авто-RPE, пересчёт по новому e1RM

Статус: принято владельцем, не реализовано
Дата: 31 октября 2026
Основание: переделка планирования в приложении — макеты и решения в репозитории `sizy-lift-app`,
`design/prototypes/program-editor-2026-11/`;
[ADR-0007](0007-two-way-sync-and-coaching.md) — синхронизация и права тренера; [web.md](../web.md) — отдельные планы.

## Контекст

Владелец решил:

1. Тренировку можно запланировать без программы — себе или, если ты тренер, подопечному.
2. RPE в плановом подходе считается сам из веса, повторов и e1RM; ручной RPE отключает расчёт для подхода.
3. Когда у упражнения новый e1RM, приложение предлагает пересчитать % и RPE в будущих тренировках.
4. Тренировку программы можно перенести перетаскиванием в календаре: на занятый день, в прошлое, после
   конца программы. Подопечный переносит тренировки программы тренера.

Что уже есть на сервере:

- `standalone_workout` (миграция 018) и `/api/v2/web/standalone-workouts/{id}` — отдельный план для веба.
  Своя ревизия, пишет только владелец, тренер только читает, в sync v2 его нет.
- Перенос `workout_reschedule` (миграция 013): пишет только подопечный, `program_id NOT NULL`, push и событие
  «Входящих» тренеру.
- `planned_set.target_rpe_tenths` — 5,0–10,0 с шагом 0,5. Признака «посчитан или введён вручную» нет.
- e1RM сервер не хранит и не считает ([coach-workspace.md](../coach-workspace.md), раздел 3): калькулятор один,
  на TypeScript, общий у телефона и веба.

## Решение коротко

| Тема | Решение | Отвергнуто |
| --- | --- | --- |
| Разовая тренировка | Новый тип агрегата sync v2 `standalone_workout` с правами как у программы | Скрытая программа-контейнер на телефоне; программа из одной недели на каждую разовую |
| «В программу» | Обычная тренировка программы, сервер не меняется | — |
| Авто-RPE | Хранить признак `targetRpeAuto` в плановом подходе; значение считает клиент | Хранить только ручной RPE, посчитанный — вычислять при показе |
| Новый e1RM | Замечает клиент. Свою программу пересчитывает владелец, программу тренера — тренер | Событие `max_updated` с расчётом e1RM на сервере; право подопечного править цели в чужой программе |
| Перенос | Своя программа — запись программы; программа тренера и разовая тренера — `workout_reschedule` | — |
| Перенос в прошлое | Без особых правил: невыполненная тренировка в прошлом — пропуск (`workout_missed`) | Перенос в прошлое только вместе с отметкой «выполнено» |

## 1. Разовая тренировка — тип агрегата `standalone_workout`

### Данные

- Код типа `standalone_workout`; добавляется в CHECK `published_aggregate.type`, в `AggregateType`
  (только sync v2, не в `V1`), в `AccessPolicy`.
- Payload — `StandaloneWorkoutPayloadV1`: `ProgramPayloadV1.PlannedWorkout` (блоки, упражнения, подходы,
  `targetPercentOneRmTenths`, `targetRpeAuto`) плюс `updatedAt`. Дата — `workoutDate` самой тренировки.
- Хранение остаётся в `standalone_workout` (JSONB): разовая читается и пишется целиком, нормализация в
  таблицы программы не нужна. Колонка `revision` таблицы перестаёт быть источником ревизии: ревизия, автор,
  tombstone и версии клиентов — общие, `published_aggregate` и `aggregate_client_version`, как у остальных типов.
- `original_date` больше не нужна: перенос — отдельный агрегат (ниже). Колонку удаляет миграция вместе с
  переходом на общие ревизии.

### Права

| Кто | Видит | Пишет |
| --- | --- | --- |
| Владелец | свои | создаёт, правит, удаляет свои; разовую тренера только читает |
| Активный тренер | все разовые подопечного | создаёт новые (`ownerId` подопечного), правит и удаляет только созданные им |

Как у программы: один писатель — `published_aggregate.author_user_id`; создание тренером ставит автора;
разрыв связи сбрасывает автора, разовые тренера остаются у подопечного его собственными. Упражнения тренера
в разовой копируются в библиотеку подопечного тем же механизмом, что для программы
([coaching.md](../coaching.md), «Упражнения тренера в программе подопечного»).

### Уведомления и «Входящие»

- Новый вид push `workout_planned` подопечному: тренер создал или изменил его разовую. Склейка по агрегату,
  как у `program_updated`. Заголовок без данных: «Тренер запланировал тренировку».
- `workout_missed` ежедневная задача считает и для разовых: дата (с учётом переноса) раньше вчерашнего дня,
  нет завершённой тренировки с `planned_workout_id` = id разовой. `subject_id` — id разовой.
- `program_ending` разовых не касается.

### Связь с фактом

Без изменений: фактическая тренировка ссылается на план через `workout.plannedWorkoutId`. Id разовой
уникален среди плановых тренировок владельца, как и сейчас проверяет `programIdExists`.

### Веб

`/api/v2/web/standalone-workouts/{id}` переводится на ту же службу записи, что и sync v2: те же права,
ревизии и фан-аут, тренер получает право записи. Позже веб пишет через `POST /api/v2/sync/push`,
и REST-ресурс удаляется. Существующие строки миграция регистрирует в `published_aggregate` и засевает в ленты
владельца и активного тренера.

## 2. Перенос

- **Своя программа**: перенос — смена `workoutDate` в программе; за концом программы приложение добавляет
  недели. Обычная запись `program`.
- **Программа тренера и разовая тренера**: `workout_reschedule`. `programId` становится необязательным
  (`program_id` — `NULL` для разовой). Перенос разовой на её исходную дату — снятие переноса, как у программы.
  Удаление разовой снимает её перенос каскадом.
- Свою разовую владелец переносит записью самой разовой, перенос ему не нужен.
- Ограничений нет: два плана в один день, дата в прошлом, дата после конца программы допустимы.
  Невыполненный план с датой в прошлом даёт тренеру `workout_missed` — это и есть пропуск.

## 3. Авто-RPE

- В плановый подход (программа и разовая) добавляется `targetRpeAuto: boolean`, по умолчанию `false`.
  Колонка `planned_set.target_rpe_auto boolean NOT NULL DEFAULT false`; в JSON разовой — то же поле.
- `true` — `targetRpeTenths` посчитан клиентом из веса, повторов и e1RM и будет пересчитываться;
  `false` — введён вручную или не задан. Сервер значение не считает и не проверяет, как вес по проценту.
- Шкала прежняя, 5,0–10,0: расчёт ниже 5 клиент оставляет пустым (`targetRpeTenths = null`,
  `targetRpeAuto = true` — следующий расчёт его заполнит).
- Формула (клиент): `RPE = 10 − (кривая⁻¹(вес / e1RM) − повторы)` по кривой Nuzzo 2024 из калькулятора e1RM,
  округление до 0,5.
- Старый телефон поле не знает и при записи программы теряет его — посчитанные RPE становятся «ручными».
  Это безопасно (числа не меняются, только перестают пересчитываться) и пройдёт с обновлением приложения.
- Общие тестовые данные публикации (`src/test/resources/publication`) обновляются вместе с приложением.

## 4. Пересчёт по новому e1RM

- e1RM по-прежнему считает только клиент. Сервер ничего не добавляет.
- **Своя программа и свои разовые**: телефон после тренировки с новым e1RM показывает предложение и при
  согласии переписывает будущие плановые подходы обычной записью агрегатов. Пересчитываются вес по проценту
  (где задан процент) и RPE с `targetRpeAuto = true`. Ручные RPE не трогаются.
- **Программа и разовые тренера**: подопечному предложения нет — он их не пишет. Предложение видит тренер
  (телефон и веб): e1RM подопечного он считает по его тренировкам, которые и так получает.
- В предложении ссылка на тренировку, где установлен e1RM: если рекорд случайный, тренировку правят,
  а план не пересчитывают.
- Предложение написано для начинающих: что такое e1RM, что поменяется и почему. Пример текста:
  «Новый расчётный максимум в жиме: 105 кг вместо 100. Это вес, который, судя по последней тренировке, вы
  подняли бы один раз. Веса, заданные в процентах от максимума, и посчитанный RPE (насколько тяжело будет
  подходу) в будущих тренировках можно обновить под него. Ваши ручные значения останутся как есть».

## Порядок работ

1. Сервер: `targetRpeAuto` (миграция, payload, фикстуры).
2. Сервер: тип `standalone_workout` в sync v2 — права, фан-аут, миграция существующих строк, перевод
   веб-ресурса на общую службу.
3. Сервер: `workout_reschedule` с необязательным `programId`, push `workout_planned`, `workout_missed` для разовых.
4. Телефон: синхронизация разовых, авто-RPE, пересчёт по e1RM, календарь и перенос.
5. Веб (`sizy-lift-frontend`): запись разовых тренером, `targetRpeAuto`, предложение пересчёта тренеру.

## Последствия

- Разовая — полноправные данные: синхронизация, конфликты, авторство, удаление аккаунта, «Входящие».
- Сервер по-прежнему не считает ни e1RM, ни RPE, ни вес по проценту.
- Старые клиенты разовых не видят (тип только в sync v2) и теряют признак авто-RPE при записи программы.
