# Архитектура

Сервер находится в отдельном репозитории `VLmb/sizy-lift-backend`. Это уточняет
первоначальное размещение `apps/server` из ADR-0004 мобильного репозитория.

## Принятые решения

- Java 25, Spring Boot, Gradle Wrapper с Kotlin DSL.
- Модульный монолит, Spring MVC, PostgreSQL, Liquibase с SQL changeset-файлами.
- Обычная слоистая архитектура: `controller → service → repository`.
  Контроллеры принимают HTTP-запросы и работают с DTO, сервисы реализуют бизнес-логику
  и определяют границы транзакций, репозитории отвечают за доступ к данным.
  Классы группируются по функциональности (package by feature): будущие `identity`,
  `publication`, `workouts`. Внутри feature используются пакеты `controller`, `service`,
  `repository`, а также `dto` и `entity` по мере необходимости. Пустые слои заранее
  не создаются.
- Доступ к БД — `JdbcTemplate` и SQL вручную, без JPA/Hibernate. Публикация заменяет
  агрегаты целиком пачками `INSERT`, а чтение (в том числе для MCP) — выборки с фильтрами
  и агрегатами; ORM здесь только мешает. Схемой владеет Liquibase.
- Версионируемый REST API (`/api/v1`) для мобильного клиента.
- Первый обмен данными — контролируемая односторонняя публикация из локальной
  SQLite: outbox, пакетная отправка, стабильные идентификаторы операций,
  идемпотентное применение и подтверждение сервером. Kafka сейчас не требуется.
- Синхронизация в обе стороны, данные тренера, ИИ-импорт и push-уведомления — ADR в
  [`adr/`](adr/) (0007–0009, статус «предложено»). Общая схема таблиц и пакетов —
  [ADR-0010](adr/0010-data-model-and-architecture.md). Номера продолжают ADR приложения.

## Аутентификация

Keycloak управляет регистрацией через email/пароль, подтверждением почты,
восстановлением доступа и входом через Google/Facebook. Бэкенд — OAuth 2.0 resource
server: Spring Security проверяет подпись, срок, `iss` и `aud` access token. Аккаунт
SizyLift (`identity.user_account`) связан с внешней идентичностью по `issuer` и `sub`
и создаётся при первом запросе. Мобильный клиент использует системный браузер и
Authorization Code + PKCE, секреты провайдеров не попадают в клиент.

Все запросы, кроме `/actuator/health`, требуют токен. Подробности, параметры клиента
и контракт для мобильного приложения — [authentication.md](authentication.md).

## Публикация данных

Feature `publication`: приём пачек агрегатов с телефона (`POST /api/v1/publication/batch`),
без пользовательских настроек: после входа копируется всё. Реляционная копия тренировок, планов, своих упражнений,
профиля и здоровья с `user_id` в ключах; системный каталог упражнений — общий. Подробности —
[publication.md](publication.md).

## Синхронизация v2

Feature `sync` вырастает из `publication` и использует её publisher'ы и readers: запись с базовой
ревизией и last-writer-wins (`POST /api/v2/sync/push`), журнал конфликтов и персональная лента
изменений с курсором (`GET /api/v2/sync/changes`). Публикация v1 продолжает работать и тоже попадает
в ленту. Подробности — [sync.md](sync.md), решения — [ADR-0007](adr/0007-two-way-sync-and-coaching.md).

## Тренер и подопечный

Feature `access` — `AccessPolicy`, единственное место решений о чужих данных: запись, чтение ленты
и фан-аут. Feature `coaching` — режим тренера, приглашения (хранится только хеш токена), связи,
разрешение на травмы и разрыв с передачей программ подопечному. Подробности — [coaching.md](coaching.md).

## Push-уведомления

Feature `notifications`: устройства (`/api/v2/devices`), транзакционный outbox и отправка в Expo
фоновыми задачами с `SKIP LOCKED`. О тренировках не знает: уведомление ставят `sync` и `coaching`
в транзакции изменения. Подробности — [notifications.md](notifications.md).

## ИИ-импорт программ

Feature `imports`: сессии импорта, разбор текста и таблиц (`.xlsx`, CSV, Google Таблицы по ссылке),
вызов модели за интерфейсом `ProgramParserModel` (DeepSeek) вне транзакции и детерминированная сборка
черновика программы. Длинные внешние вызовы идут на виртуальных потоках
(`spring.threads.virtual.enabled`), одновременные вызовы модели ограничены общим `Semaphore`.
Подробности — [imports.md](imports.md).

## Конфигурация и развёртывание

Настройки разделены на профили Spring `dev` и `prod` (YAML). Production работает на
одном сервере в Docker Compose: Caddy с HTTPS, бэкенд, Keycloak в optimized-режиме и
две отдельные PostgreSQL. См. [deployment.md](deployment.md).
