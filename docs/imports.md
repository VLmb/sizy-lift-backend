# AI-импорт программ v1

Серверная часть. Веб-интерфейс — в `sizy-lift-frontend`, описание — `docs/ai-import.md` этого репозитория.
Обычный путь: источник → план DeepSeek (небольшая программа разбирается в том же запросе,
большая — параллельно по частям) → текстовые уточнения при необходимости →
выбор упражнений → атомарное создание программы → обычный редактор.

## Настройка и библиотеки

- JDK 25, Spring Boot 4.1.1; используется существующий MVC/JDBC/PostgreSQL стек.
- Транспорт DeepSeek — собственный потоковый клиент на Spring `RestClient` (`DeepSeekProgramParser`):
  OpenAI-совместимый `/beta/chat/completions` со `stream:true`, `thinking` выключен, `strict` tools,
  без agent/tool execution loop и скрытых повторов. Модель явно задана `deepseek-flash`.
  `spring-ai-deepseek:2.0.2` больше не используется кодом и может быть удалён вместе с обновлением lock-файла.
- `poi-ooxml:6.0.0`: XLS и XLSX, координаты, листы, объединения, отображаемые проценты;
  Java 17+ совместим с JDK 25. Формулы не вычисляются.
- `commons-csv:1.14.1`: CSV с кавычками и переносами строк, без обязательного шаблона колонок.
- `json-schema-validator:3.0.8`: серверная проверка той же схемы на Jackson 3.
  Схема статическая, встроенная в classpath, без внешних `$ref`.

Версии проверены по первичным источникам и закреплены Gradle lock-файлом:
[Spring AI](https://docs.spring.io/spring-ai/reference/getting-started.html),
[DeepSeek API-модуль](https://docs.spring.io/spring-ai/reference/api/chat/deepseek-chat.html),
[POI](https://poi.apache.org/download.cgi),
[CSV](https://commons.apache.org/proper/commons-csv/download_csv.cgi),
[networknt](https://github.com/networknt/json-schema-validator).
Свой клиент вместо SDK: нужен поток фрагментов аргументов инструмента для прогресса, поле кэша
DeepSeek `prompt_cache_hit_tokens` и контроль простоя соединения; всё это — несколько десятков строк.
LangChain4j и агенты здесь не нужны: состояние процесса принадлежит сессии импорта.

В `deploy/.env` для production:

```dotenv
AI_IMPORT_ENABLED=true
DEEPSEEK_API_KEY=<ключ только на сервере>
DEEPSEEK_API_URL=https://api.deepseek.com
```

Compose передаёт эти переменные backend. Без включения импорт возвращает 503 при создании
и отправке ответов; существующие сессии доступны для чтения, выбора упражнений и commit.
При включённой функции пустой ключ — ошибка старта. Адрес и ключ production не имеют
значений по умолчанию в `application-prod.yaml`. Для dev задайте
`SIZYLIFT_IMPORTS_ENABLED=true` и `SIZYLIFT_IMPORTS_DEEPSEEK_API_KEY`.
Таймаут провайдера по умолчанию 5 минут, аренда worker — 10 минут.

## HTTP API

Все запросы требуют access token Keycloak. Инициатор — `user_account.id`, не token sub.
`ownerId` задаётся при создании и дальше не меняется. Сессию читает только инициатор,
при этом доступ к подопечному проверяется заново на каждом действии.
Чужая сессия и отозванная связь дают 404. Истёкшая сессия — 410.

### Создание

`POST /api/v2/imports`, JSON → **202** `{id,status,version}`:

```json
{
  "requestId": "уникальный UUID операции",
  "ownerId": null,
  "source": "text",
  "text": "Пн: присед 3×5 100 кг @8",
  "name": "Силовой блок",
  "startDate": "2026-11-09",
  "language": "en"
}
```

`startDate` обязателен и задаёт календарное размещение программы. `name` необязателен,
без него используется «Импортированная программа» или `Imported program` для английского интерфейса;
его можно изменить через PATCH. Необязательный `language` — `ru` (по умолчанию) или `en`.
Он управляет языком уточняющих вопросов, но не переводит названия и заметки исходника.
Язык фиксируется при первом создании сессии и хранится после перезапуска worker. Повтор
с тем же `requestId` не меняет язык и не создаёт новую сессию; язык не включён в хэш
содержимого запроса, чтобы сохранить совместимость с существующими повторными запросами.
Для ссылки: `source:"sheet"`, `url`, без `text`. Используется существующий публичный
CSV-экспорт Google Sheets: `gid` из ссылки или первый лист. Для закрытой таблицы
нужна загрузка Excel, делать документ публичным необязательно. OAuth в эту версию не входит.

Для файла: тот же URL, `multipart/form-data`, часть `metadata` с Content-Type
`application/json` (поля выше, `source:"file"`, без text/url), часть `file` — XLSX/XLS/CSV.
Тип содержимого проверяется по сигнатуре, расширение не является доказательством формата.
CSV — UTF-8 или Windows-1251. Скрытые листы Excel пропускаются; видимые сохраняют порядок.
Пустые CSV-строки сохраняют нумерацию координат, разделители в кавычках не меняют CSV-диалект.
Ячейки с формулами используют сохранённый результат, а не вычисляются на сервере;
отсутствующий результат XLSX помечается явно вместо подстановки нуля.

Google-документ должен читаться без входа: «Все, у кого есть ссылка → Читатель».
Отдельно публиковать его в интернете не требуется. Google cookie и токены пользователя не передаются;
страница входа, 401/403/404 и запрет CSV-экспорта дают `sheet_unavailable`. Скачивается одна вкладка
со снимком данных на момент обработки, не постоянная синхронизация. Все вкладки можно передать XLSX.

Повтор `requestId` с тем же содержимым возвращает ту же сессию без нового задания.
Изменённое содержимое при том же ключе — 409. Для исправленного исходника создаётся новая сессия.

### Состояние

`GET /api/v2/imports/{id}` → **200**:

- `id`, `ownerId`, `status`, `version`, `round`, `name`, `startDate`, `expiresAt`;
- `needsClarification`, `clarificationMessage`, `draft` (`ImportDraftV1`);
- `source.items:[{ref,text}]` — нормализованный источник для показа цитат;
- `decisions` — решения по `exerciseResolutions[].key`;
- `canCommit`, `program` (`ProgramPayloadV1`, либо null до завершения выбора), `warnings`;
- `error:{code,message}` либо null;
- `inputTokens`, `outputTokens`, `reservedCostMicros`, `receipt` после сохранения.

Состояния: `queued → processing → clarification_required → queued → processing → review → committed`.
Также `failed`, `cancelled`, `expired`. `review` с `canCommit:false` требует выбора упражнения.
Интерфейс опрашивает состояние каждые 1–2 секунды только пока открыт экран обработки.
Не показывать фиктивный процент генерации — только `progress`.

`progress` есть только в `processing`, иначе null: `{stage, exercises, weeksDone, weeksTotal}`.
`stage:"plan"` — составляется план: `exercises` — сколько упражнений модель уже выписала, `weeksTotal` —
сколько недель в плане (null, пока план не начат), `weeksDone` — недели, разобранные в том же ответе.
`stage:"weeks"` — недели разбираются частями: `weeksDone` из `weeksTotal` — завершённые части плюс недели,
полностью выписанные в потоке ответа. Числа реальные и не убывают; запись — не чаще раза в секунду.

### Уточнение

`POST /api/v2/imports/{id}/clarifications` → **202**, тот же View:

```json
{"requestId":"UUID ответа","version":3,"round":0,"answer":"От первого рабочего подхода"}
```

Нужны текущие `version` и `round` из GET. Повтор того же ответа не создаёт LLM-запрос.
Переиспользование ключа с другим ответом и ответ на устаревший вопрос — 409.
Модель получает исходник, тот же каталог alias/названий и **все** вопросы с ответами,
а не только последний. Черновик прошлого раунда не передаётся: задавая вопрос, модель программу
не разбирает, поэтому ожидание и оплата вывода не удваиваются на каждом уточнении.
Сессии одного пользователя изолированы по importId. Максимум три ответа пользователя;
если модель снова требует уточнение, статус `failed`, код `clarification_limit`.
Технический сбой провайдера не превращается в вопрос пользователю.

### Выбор упражнений и метаданные

`PATCH /api/v2/imports/{id}` → **200**, View:

```json
{
  "version": 6,
  "name": "Изменённое название",
  "startDate": "2026-11-09",
  "decisions": [{"key":"exercise-key","kind":"existing","exerciseId":"UUID каталога"}]
}
```

Создание своего:

```json
{
  "version": 6,
  "decisions": [{
    "key":"exercise-key","kind":"new","name":"Моё упражнение",
    "resultType":"weight_reps","liftClass":"basic"
  }]
}
```

Результат модели `matched` выбирается сразу. `ambiguous` не имеет решения до выбора пользователя.
`new` с известным типом подготавливается автоматически с классом `other`; параметры можно изменить.
Если тип неизвестен, требуется заполнить форму создания. У всех строк остаётся поиск по полному
текущему каталогу и «Создать своё», включая упражнения, добавленные после LLM-разбора.
Типы: `weight_reps`, `added_weight_reps`, `duration`, `distance_time`, `free`.
Классы `sbd`/`basic` разрешены только для `weight_reps`, как при обычной записи.
Несовместимое с подходами упражнение отклоняется без потери черновика.

`key` (`e1`, `e2`, …) объединяет повторные ссылки на **одно** упражнение. Разные варианты одного названия
в разных контекстах должны иметь разные ключи. UUID нового упражнения выдаёт сервер,
стабильно для пары importId/key; присланный клиентом UUID нового упражнения не используется.
До commit библиотека не меняется. Повторный PATCH со старой версией — 409, нужно перечитать GET.

### Сохранение и отмена

`POST /api/v2/imports/{id}/commit`, `{ "version": 7 }` → **200**:
`{id,ownerId,programId,programRevision}`. Кнопка «Создать программу» / «Отправить …»
показывает количество новых упражнений. Статус программы — `draft`, активация остаётся
обычным действием редактора. После ответа перечитать программу обычным web API:
при тренерском сохранении ссылки упражнений могли быть переписаны.

`ImportCommitService` держит общую транзакцию с квитанцией импорта. Новый метод
`SyncPushService.createImportedProgram` допускает только создание упражнений инициатора
и одной программы, проверяет отказ каждого агрегата и не разрешает заменять существующие.
Используются штатные publishers, AccessPolicy, CoachExerciseAdoption и fan-out.
События пачки откладываются до записи всех агрегатов, курсоры лент блокируются в общем
порядке UUID. При отказе откатываются также уведомления и строки лент.
Обычный `/sync/push` сохраняет прежнюю семантику отдельных транзакций.

Повтор commit возвращает ту же квитанцию и ничего не перезаписывает, даже если программу
уже правили в редакторе. Конкурентные commit сериализуются блокировкой сессии.
Тренерское упражнение сначала создаётся у тренера, затем штатно копируется подопечному.

`DELETE /api/v2/imports/{id}` → **204**, удаляет временное содержимое и отменяет задание.
Сохранённую программу этим API удалить нельзя. Поздний ответ модели не применяется;
уже отправленный провайдеру запрос всё ещё может быть оплачен.

## Модель и валидация

### Разбор в два этапа

Время ожидания определяется в основном числом выходных токенов одного ответа. Поэтому:

1. **План** (`emit_program_plan`, `program-import.plan.v1.schema.json`). Модель либо задаёт вопрос, либо
   перечисляет все упражнения и все недели (`plan[]`: `week`, `cycle`, `name`, `workouts`). Если тренировок
   не больше `single-call-workouts`, она в том же ответе подробно разбирает и `weeks` — небольшая программа
   обходится одним запросом. Вопрос приходит за секунды: подходы при этом не генерируются.
2. **Недели по частям** (`emit_program_weeks`, `program-import.weeks.v1.schema.json`). Недели плана делятся
   на части подряд примерно по `workouts-per-chunk` тренировок (не больше `max-chunks` частей) и разбираются
   параллельно, не больше `chunk-parallelism` запросов на сессию. Ожидание — примерно время самой долгой части,
   а объём программы не ограничен выводом одного ответа. Часть получает id упражнений плана; пропущенное
   в плане упражнение она добавляет как `n1…`, сервер даёт ему ключ `k{первая неделя части}n{i}` и объединяет
   с уже известным упражнением с тем же названием и решением.

План хранится в `import_session.outline` (миграция 031): после перезапуска worker недели разбираются
без повторного плана. Ответ на вопрос и завершение раунда план очищают.

Каждая часть повторяется внутри той же аренды, без очереди: невалидный ответ — один раз с конкретными
ошибками, 429/5xx — после короткой паузы с учётом Retry-After. Обрезанная часть делится пополам;
обрезанная одна неделя — `input_too_large`. Если по лимиту обрезан сам план с неделями, он сразу
запрашивается заново без недель. Число вызовов по частям ограничено, первая неустранимая ошибка
отменяет остальные части. Аренда продлевается перед каждым вызовом; отмена сессии останавливает
следующие вызовы, а поздний результат не записывается.

Оба инструмента передаются в каждом запросе в одном порядке, а меняется только конец входа — раздел ЗАДАЧА.
Префикс (инструкции, схемы, каталог, источник, ответы) совпадает у плана и всех частей и попадает в кэш DeepSeek:
повторная отправка источника в каждой части стоит как кэш-попадание.

### Ответ модели

Модель отвечает в компактном формате (DTO `ImportModelDraft`), сервер переводит его в `ImportDraftV1`:

- `question` — вопрос пользователю; если он не пуст, остальное игнорируется и не разбирается моделью;
- `exercises[]`: `id` (`e1`…), `name` из источника, `status`, `match` — alias каталога (`c1`…),
  `candidates` — alias, `newName`, `resultType`, `refs`. UUID каталога модель не видит и не пишет:
  короткий alias дешевле и не допускает опечатки в ID;
- `plan[]`: `week` — общий номер, `cycle` — название цикла (соседние недели с одинаковым `cycle` — один цикл),
  `name`, `workouts`;
- `weeks[]`: `week`, `days[]` с `day` 0–6 от начала недели (сервер считает `dayOffset = 7·(week−1) + day`),
  `blocks[]`, `items[]`; недели ответа должны совпасть с планом или с неделями ЗАДАЧИ;
- `items[]`: `ex`, `note`, `refs` (минимум одна ссылка на строки упражнения и его предписания), `sets`;
- подход — строка `"n=3 r=5 kg=100 rpe=8 type=working | заметка"`. Поля: `n`, `r` (число, `8-12`, `AMRAP`),
  `kg`, `pct`, `sec`, `m`, `rpe`, `rir`, `rest` (секунды), `type`. Отсутствующее поле — неизвестное значение.

Ключи узлов, циклы и `dayOffset` назначает сервер; `sourceRefs` подхода — ссылки его упражнения.
Упражнения, не использованные в программе, отбрасываются и не попадают в выбор.
Вход модели — текст, а не JSON (`ModelInputRenderer`): разделы КАТАЛОГ, ДАТА СТАРТА, ИСТОЧНИК, ОТВЕТЫ ПОЛЬЗОВАТЕЛЯ,
ЗАДАЧА, ОШИБКИ ПРЕДЫДУЩЕГО ОТВЕТА. Переносы и табуляции внутри значений экранируются. Каталог идёт первым
(общие упражнения, затем свои) — префикс запроса совпадает и между импортами.

Текст в ИСТОЧНИКЕ — строки `text:N<TAB>строка`. Лист XLS/XLSX и CSV — сеткой: заголовок с правилом ref
(`ЛИСТ sheet:0<TAB>название, ref ячейки: sheet:0!столбецстрока`), строка непустых столбцов и непустые строки
с номером в начале. Модель видит расположение ячеек, а координата не повторяется в каждой ячейке, поэтому
вход таблиц заметно короче. ref ячеек (`sheet:0!B3`, `csv:3:2`) и их проверка не изменились;
объединения ячеек перечисляются после сетки своего листа.

Ответ модели читается потоком (SSE). Фрагменты аргументов инструмента считаются по ходу генерации:
законченные элементы `exercises`, `plan` и `weeks` дают прогресс сессии. Простой потока дольше минуты
или превышение `timeout` закрывает соединение — это обычный технический сбой с повтором.

### ImportDraftV1

DTO API и хранения — `ImportDraftV1`, клиенты его не меняют.
Вложенность: cycles → weeks → workouts → blocks → exercises → sets.
Числа в IR представлены строками; `""` означает неизвестное, а не ноль.
У prescription есть `count`, `repetitions`, `weightKg`, `percentOneRm`, `durationSeconds`,
`distanceMeters`, `rpe`, `rir`, `restSeconds`, `setType`, `note`, `sourceRefs`.
`count` описывает одинаковые подходы, код разворачивает их; UUID модель не генерирует.
`dayOffset` — дни от даты старта всей программы, номера недель общие для всех циклов.

Resolution: `key`, `originalName`, `status:matched|ambiguous|new`, `exerciseId`,
`candidates`, `proposedName`, `proposedResultType`, `sourceRefs`. Для неизвестных
строковых значений используется `""`, для отсутствующих кандидатов — `[]`.
Source refs: `text:N`, `csv:row:column`, `sheet:index!A1`, `sheet:index!merge:A1:C1`,
а также `answer:N` — ссылки на ответы пользователя, начиная с 1.

Сервер проверяет JSON Schema ответа, размеры, уникальность id и номеров недель, существование ссылок,
alias каталога, исходное название упражнения и допустимость полей подхода. Ошибки собираются
с указанием места в терминах ответа модели (например,
`weeks[week=2].days[0].blocks[1].items[0].sets[0] «3x5»: фрагмент «3x5» не поле …`), до десяти за раз.
Словесные числа и смысл предписаний интерпретирует модель; обязательное совпадение с цифрами
в источнике отвергало бы корректные фразы вроде «три подхода по пять».
Проверка схемы и ссылок не является доказательством смысловой точности LLM.
Неоднозначную семантику модель должна вынести в clarificationMessage.

`ProgramDraftCompiler` не вызывает defaultSet и auto-RPE. Неизвестные поля остаются null;
неизвестное количество подходов не создаёт условные три подхода: предписание остаётся
в комментарии упражнения. Диапазоны повторений, AMRAP и RIR сохраняются в заметках с предупреждением.
Кг переводятся в граммы, секунды — в миллисекунды; округление веса до грамма явно отмечается.
Проценты остаются в native поле, backend не изобретает ПМ и абсолютный вес.
Проценты, недоступные классу упражнения, и неподдерживаемый RPE остаются в заметках.
Технический `working` у подхода без типа сопровождается заметкой, что тип не указан.

## Очередь, ограничения и приватность

Таблица `import_session`, миграции 029–030. Создание и ответ на вопрос после commit транзакции
сразу будят worker (`ImportQueued`), не дожидаясь следующего опроса очереди. Worker использует аренду и SKIP LOCKED; общая
блокировка admission делает квоты атомарными, а блокировка claim ограничивает число
активных запросов между несколькими backend-процессами. Вызов модели не держит транзакцию БД.
Каждая запись результата проверяет lease token: отмена, истечение и новый worker защищены
от позднего ответа предыдущего процесса. После перезапуска задание подбирается по истёкшей аренде.

Настраиваемые `sizylift.imports.*` defaults:

| Параметр | Значение |
|---|---:|
| retention | 24h |
| daily-limit | 20 за последние 24 часа |
| active-per-user | 2 незавершённых сессии |
| concurrent-requests | 4 на сервис |
| clarification-rounds | 3 |
| attempts-per-round | 2, включая первоначальный вызов |
| max-file-bytes / max-expanded-bytes | 5 / 50 МиБ |
| max-sheets / max-cells | 10 / 20 000 |
| max-source-chars | 200 000 |
| max-output-tokens | 32 768 |
| max-cost-micros | 1 000 000 микродолларов = $1 верхнего бюджета |
| input-micros-per-million / output-micros-per-million | 300 000 / 1 200 000 |
| single-call-workouts | 8 тренировок — до этого объёма программа разбирается одним запросом |
| workouts-per-chunk / max-chunks | 12 тренировок / 8 частей |
| chunk-parallelism | 8 одновременных запросов на сессию |

Одновременно к провайдеру уходит не больше `concurrent-requests × chunk-parallelism` запросов.
Резерв бюджета считается на каждый вызов, включая части; `attempts-per-round` ограничивает вызовы плана.

Дополнительно: 2000 строк/лист, 256 столбцов, 4000 символов/ячейку, 2 МиБ ответа провайдера.
Вход не обрезается, превышение приводит к понятной ошибке. Multipart контейнера ограничен 5/6 МиБ.
Проверяются расширение/сигнатура и полный объём ZIP до открытия workbook.
Google-ссылки проходят существующий allowlist и ограничения всех redirect в SheetImportService.

Перед каждым платным вызовом резервируется верхняя оценка бюджета: не более одного токена
на байт UTF-8 контекста, запас на инструкции/схему и максимальный output, по пиковому прайсу
$0.30/$1.20 за миллион input/output. `reservedCostMicros` — **не счёт провайдера**:
резерв не возвращается при сетевом сбое или после кэширования. Usage отражает полученные ответы;
дополнительные cache-hit поля, отсутствующие в SDK Usage, могут остаться нулевыми.
При изменении тарифов обновить `input-micros-per-million` / `output-micros-per-million`. Timeout/crash может привести к повторной
оплате — гарантируется идемпотентность программы, не exactly-once HTTP у провайдера.

Для плана 429 и временные 5xx повторяются один раз, учитывая Retry-After и jitter через очередь,
без блокирующего sleep. Невалидный ответ получает одну техническую попытку сразу, без паузы:
список конкретных ошибок сохраняется в `import_session.repair_hint` (миграция 030) и передаётся модели
в разделе ОШИБКИ ПРЕДЫДУЩЕГО ОТВЕТА, чтобы повтор исправлял их, а не был случайной перегенерацией.
Ответ, обрезанный по `max-output-tokens` (`finish_reason=length`), тем же запросом не повторяется:
план запрашивается без недель, часть делится пополам (см. «Разбор в два этапа»). usage обрезанного ответа учитывается.
4xx конфигурации не повторяются. В SDK скрытые retries и исполнение tools не включаются.

Raw-файл удаляется после нормализации. После commit содержимое, каталог, ответы и черновик
стираются сразу, остаётся квитанция. Через 24 часа остальные сессии очищаются и становятся expired.
Минимальные записи с ключами идемпотентности удаляются через 30 дней после expiresAt;
удаление аккаунта каскадно удаляет его сессии. Активные пользовательские программы не затрагиваются.

В модель не отправляются профиль, история, ПМ или медицинские данные из БД. Сам источник
может содержать личные сведения: перед выпуском интерфейса нужно уведомление о передаче
внешнему провайдеру и соответствующая политика. Zero retention провайдера не обещается.
Сообщения ошибок безопасные, тела HTTP и исходные исключения в логи не пишутся.
Метрики `sizylift.import.requests`, `.duration`, `.tokens` не содержат пользовательских тегов.

## Проверки

`./gradlew build` на JDK 25 с Docker и настоящим PostgreSQL. Тесты импорта подменяют только
LLM транспорт: реальных платных вызовов нет. Проверяются контекст и все раунды, каталог,
source extraction, multipart, отмена, TTL, квоты, бюджет, отзыв прав, собственные упражнения,
копирование тренера, идемпотентность, конкурентный commit и реальный SQL-откат при коллизии ID.
`ImportTranscriptionTest` сравнивает **полный** нормализованный источник XLS/XLSX/CSV с эталоном:
координаты, листы и порядок, проценты, числа с запятой, даты, время, cached formulas, ошибки ячеек,
объединения, скрытые листы, пустые строки, кавычки, переносы и Windows-1251. Интеграционный XLSX-тест
проверяет источник, переданный модели, и вес/проценты/повторения в реально сохранённом payload.
`SheetImportServiceTest` проверяет gid, redirects, отсутствие авторизации Google, приватные документы,
HTML вместо CSV и ограничение потока. Реальный Google не вызывается.
Тест параллельных worker удерживает четыре модельных запроса, проверяет отказ пятого claim и его
исполнение после освобождения места. Ограничение действует через PostgreSQL, а не только semaphore процесса.
Перед включением в production дополнительно прогнать согласованный обезличенный корпус
программ на настоящем DeepSeek и измерить точность, latency и фактический расход токенов.
