# Тренер и подопечный

Контракт `/api/v2/coaching`: режим тренера, приглашения, связи, разрешение на травмы, разрыв.
Функциональное описание — ADR-0006 приложения, решения сервера — [ADR-0007](adr/0007-two-way-sync-and-coaching.md)
(разделы 5–6). Данные тренер получает и пишет через синхронизацию v2 ([sync.md](sync.md)).

Статус: реализовано (этап 3). Уведомления тренеру о принятии приглашения — вместе с push-уведомлениями
(ADR-0009, этап 5). Переносы тренировок и комментарии — этап 4.

## Кто что видит и пишет

Решает `AccessPolicy` (пакет `access`), одно место для записи, чтения и фан-аута в ленты.

| Тип агрегата подопечного | Тренер видит | Тренер пишет |
| --- | --- | --- |
| `workout`, `exercise`, `athlete_profile`, `one_rep_max` | да | нет |
| `program` | да | создаёт новые; правит и удаляет только созданные им |
| `injury`, `contraindication` | только при `healthAccess = true` | нет |

- У агрегата один писатель: `published_aggregate.author_user_id`. `NULL` — пишет владелец. Программа,
  созданная тренером, хранится под подопечным (он владелец), автор — тренер. Подопечный её не правит:
  ни через sync v2, ни через публикацию v1 (`rejected: forbidden`).
- Обычная запись автора не меняет. Его ставит только создание программы тренером и сбрасывает разрыв связи.
- Фото не публикуются вовсе, тренеру их нечего отдавать (закреплено тестом).
- Бывший тренер и посторонние не видят и не пишут ничего.

## API

Все запросы требуют токен. Ошибки: `404` — приглашения или связи нет либо вызывающий в ней не участвует;
`410` — приглашение использовано или истекло; `403` — действие не этой стороны (приглашать без режима
тренера, менять разрешение на травмы за подопечного); `409` — состояние не позволяет (своё приглашение,
у подопечного уже есть тренер, связь разорвана).

### `GET /api/v2/coaching`

```json
{ "coachEnabled": true,
  "coach": null,
  "athletes": [ { "id": "…", "coachId": "…", "athleteId": "…", "healthAccess": false,
                  "createdAt": "…", "endedAt": null, "counterpartName": "Иван" } ] }
```

`coach` — активная связь, где вызывающий подопечный; `athletes` — где он тренер. `counterpartName` —
имя второй стороны из её опубликованного профиля (`displayName`), может быть `null`.

### `PUT /api/v2/coaching/coach-mode`

`{ "enabled": true }` → тот же ответ, что `GET`. Флаг `user_account.coach_enabled`. Выключение запрещает
новые приглашения, существующие связи остаются. Лимита подопечных нет.

### `POST /api/v2/coaching/invites` → `201`

```json
{ "token": "q3J5…22 символа", "expiresAt": "…" }
```

128 случайных бит в base64url. Токен показывается один раз; в базе хранится только SHA-256, утечка базы
не даёт рабочих ссылок. Ссылку `https://<домен>/invite/<token>` строит приложение. Приглашение
одноразовое и живёт 7 дней. Без режима тренера — `403`.

### `GET /api/v2/coaching/invites/{token}`

Что подопечный видит до принятия: `coachId`, `coachName`, `expiresAt`, `coachSees` (типы, которые тренер
увидит сразу) и `coachSeesWithHealthAccess` (с разрешением на травмы).

### `POST /api/v2/coaching/invites/{token}/accept`

Создаёт связь (ответ — связь, как в `GET`). В одной транзакции: связь, отметка о принятии и засев ленты
тренера всем, что он видит у подопечного (без травм). У подопечного один активный тренер: второй — `409`.

### `PUT /api/v2/coaching/links/{id}/health-access`

`{ "enabled": true }`, только подопечный. Включение добавляет тренеру в ленту травмы и противопоказания,
выключение — `revoke` по ним. Разорванная связь — `409`.

### `DELETE /api/v2/coaching/links/{id}` → `204`

Любая сторона. Тренеру — `revoke` по всем данным подопечного. Программы тренера переходят подопечному:
автор сбрасывается, ревизия растёт, подопечный получает их в ленту как свои редактируемые. Повторный
разрыв ничего не меняет.

## Транзакции и блокировки

Порядок блокировок общий для всех записей: аккаунт владельца данных → строка агрегата → курсоры лент
(в порядке `user_id`). Запись данных берёт аккаунт владельца разделяемо (`FOR SHARE`), изменение связи
(принятие, разрешение на травмы, разрыв) — исключительно (`FOR UPDATE`) аккаунт подопечного. Поэтому
связь не меняется, пока запись считает получателей, и тренер не получит данные после `revoke`.

## Метрики

`sizylift.coaching.events{event}`: `invite_created`, `link_created`, `link_ended`, `health_granted`,
`health_revoked`.
