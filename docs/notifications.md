# Push-уведомления

Контракт `/api/v2/devices` и поведение уведомлений. Решения — [ADR-0009](adr/0009-push-notifications.md).
Статус: реализовано (этап 5).

## Устройства

### `PUT /api/v2/devices/{id}`

`id` — id установки приложения (его генерирует приложение; тот же id — `clientId` в sync v2).
Вызывается после входа и при смене push-токена.

```json
{ "platform": "ios", "pushToken": "ExponentPushToken[…]" }
```

Ответ: `{ "id": "…", "platform": "ios", "pushEnabled": true }`, токен назад не отдаётся.

- `platform` — `ios` или `android`; `pushToken` — `ExponentPushToken[…]` (или `ExpoPushToken[…]`), `null` —
  уведомления запрещены.
- Существующий id меняет только его владелец. Чужой id — 403, даже если передать другой push-токен
  или `null`; откатываются и побочные изменения токенов. UUID установки не считается авторизацией.
- При смене аккаунта сначала снимите регистрацию через DELETE с токеном прежнего пользователя.
  Если старую регистрацию снять нельзя (например, выход был без сети), используйте новый id для
  регистрации устройства нового аккаунта. Это не требует менять clientId синхронизации.
  Передача id на основании одного только входа новым аккаунтом больше не разрешена.
- Токен снимается с других установок: переустановленное приложение или чужой аккаунт на том же телефоне
  не получают уведомления прежнего владельца.

### `DELETE /api/v2/devices/{id}` → `204`

При выходе из аккаунта. Чужое или неизвестное устройство не трогается.

## Когда уведомление ставится

Уведомление ставится в той же транзакции, что и изменение данных: нет коммита — нет уведомления
(`NotificationQueue`, вне транзакции вызов запрещён).

| `kind` | Кому | Когда |
| --- | --- | --- |
| `program_updated` | подопечному | тренер создал или изменил его программу |
| `workout_planned` | подопечному | тренер создал или изменил его разовую тренировку (ADR-0011) |
| `comment_added` | второй стороне связи | создан комментарий к тренировке подопечного (не правка) |
| `workout_completed` | тренеру | подопечный опубликовал новую тренировку (не правку) |
| `workout_rescheduled` | тренеру | подопечный перенёс тренировку |
| `invite_accepted` | тренеру | подопечный принял приглашение |

Удаления, записи самого сервера (каскады, копии упражнений) и записи без активной связи уведомлений
не дают. **Склейка:** пока в очереди есть неотправленное уведомление того же вида по тому же агрегату,
второе не ставится — три правки программы за минуту дают одно уведомление.

## Что в уведомлении

```json
{ "to": "ExponentPushToken[…]", "title": "Тренер обновил программу", "body": "Иван",
  "data": { "kind": "program_updated", "ownerId": "…", "aggregateId": "…", "actorId": "…" },
  "sound": "default" }
```

- Заголовок — общий текст вида, без данных: экран блокировки видят посторонние.
- `body` — имя второй стороны из её опубликованного профиля, если есть.
- `data` — только вид и id (`ownerId`, `aggregateId`, `actorId`; у `invite_accepted` — `linkId` и
  `actorId`). Названий упражнений, весов и текста комментариев нет.
- Получив уведомление, приложение подтягивает ленту (`GET /api/v2/sync/changes`) и только потом открывает
  экран. Потерянный push ничего не ломает: лента дочитается при следующем открытии.

## Отправка

Сверено с документацией Expo (https://docs.expo.dev/push-notifications/sending-notifications/,
обновлена 13.10.2026):

- до 100 сообщений в запросе `POST https://exp.host/--/api/v2/push/send`;
- до 1000 id в запросе квитанций `POST …/getReceipts`;
- квитанции проверять через 15 минут после отправки, Expo хранит их 24 часа;
- лимит 600 уведомлений в секунду на проект, payload сообщения до 4096 байт;
- `Authorization: Bearer <EXPO_ACCESS_TOKEN>` при включённой «enhanced push security»;
- сетевая ошибка, 429, 5xx — повтор с экспоненциальной паузой; остальные отказы сами не пройдут.

Как это работает на сервере:

1. **`NotificationSender`, раз в 5 с.** Берёт до 100 строк outbox через `FOR UPDATE SKIP LOCKED` и
   откладывает их на 2 минуты (аренда). HTTP-запрос идёт без открытой транзакции. Упавший процесс не
   теряет строки, второй экземпляр не возьмёт те же.
2. **Сообщения** — на все устройства получателя с токеном. Сообщения одной строки не делятся между
   запросами, поэтому повтор не задвоит доставленное.
3. **Тикет `DeviceNotRegistered`** сразу обнуляет токен.
4. **Сетевая ошибка, 429 или 5xx.** Повтор через 30 с, 1, 2, 4, 8 минут, всего до 6 попыток. Потом строка
   помечается брошенной (`gave_up_at`) и видна в метрике.
5. **Другой 4xx** — строка сразу брошена.
6. **Квитанции — `ReceiptChecker`, раз в 15 минут.** Проверяет тикеты строк, отправленных 15 минут –
   24 часа назад. `DeviceNotRegistered` обнуляет токен, только если устройство не перерегистрировало
   новый токен. Остальные ошибки — метрика.
7. **Очистка** отправленных и брошенных строк старше 7 дней — ежедневно ночью.

При 100 строках раз в 5 секунд сервер не приближается к лимиту Expo 600 в секунду, если у пользователей
не десятки устройств.

## Конфигурация

| Свойство | Где | Значение |
| --- | --- | --- |
| `sizylift.notifications.enabled` | `application.yaml` / `application-prod.yaml` | `false` в dev и тестах — строки копятся в outbox, Expo не вызывается; `true` в prod |
| `sizylift.notifications.expo.access-token` | `application-prod.yaml` | `${EXPO_ACCESS_TOKEN}` без значения по умолчанию |
| `sizylift.notifications.expo.url` | `application.yaml` | `https://exp.host/--/api/v2/push` |
| `sizylift.notifications.send-interval`, `receipts-interval` | `application.yaml` | `5s`, `15m` |

Тесты отправки работают с заглушкой Expo (`MockRestServiceServer`), реальных вызовов в CI нет.

## Метрики

- `sizylift.notifications.enqueued{kind,coalesced}` — поставлено или склеено;
- `sizylift.notifications.sent{kind,outcome}` — `sent`, `no_device`, `failed` (все тикеты с ошибкой),
  `retry`, `gave_up`;
- `sizylift.notifications.receipts{outcome}` — `ok`, `device_not_registered`, `error`, `unavailable`;
- `sizylift.notifications.queue.size` — неотправленных строк;
- `sizylift.notifications.queue.oldest.age` — возраст самой старой неотправленной строки, секунды.
