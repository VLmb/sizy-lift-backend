# Видео подходов и техники

Контракт видео из переделки тренерского режима, этап 3 (CR-14–CR-16). Решения и обоснования —
[ADR-0012](adr/0012-video-storage.md); комментарий к упражнению — [coaching.md](coaching.md#комментарии).

Загружают видео все клиенты: приложение (iOS, Android), PWA и сайт; смотрят тоже все. Файлы идут мимо сервера,
по подписанным ссылкам прямо в хранилище. Приложение сжимает ролик и делает превью само; браузер кладёт исходный
файл как есть, а сервер перекодирует его ffmpeg и делает превью (см. «Загрузка из браузера»). Фото тренировок
по-прежнему не публикуются.

## Ролик

| Поле | Описание |
| --- | --- |
| `id` | uuid, придумывает приложение: комментарий ссылается на ролик раньше, чем появляется сеть |
| `ownerId` | владелец — кто загрузил |
| `kind` | `set` — видео подхода, `technique` — видео техники тренера |
| `status` | `pending` — место выдано, загрузка не подтверждена; `processing` — исходник из браузера загружен, сервер его перекодирует; `ready` — можно смотреть |
| `sizeBytes`, `durationMs` | размер ролика и длина |
| `title` | название: у `technique` обязательно, у `set` — по желанию (`null` — без названия); меняется `PATCH` |
| `exerciseId`, `exerciseName` | упражнение, к которому снят ролик; название — как его видел владелец при загрузке |
| `createdAt`, `uploadedAt` | выдача места и подтверждение загрузки |
| `videoUrl`, `previewUrl`, `urlExpiresAt` | подписанные ссылки GET и срок их действия; только у `ready` |
| `usage` | где ролик используется; только владельцу, остальным `null` |

`usage`:

```json
{ "comments": [ { "commentId": "…", "ownerId": "…", "workoutId": "…", "workoutDate": "2026-11-11",
                  "workoutExerciseId": "…", "setNumber": 5 } ],
  "programs": [ { "programId": "…", "ownerId": "…", "name": "Силовой блок" } ],
  "exercises": [ { "exerciseId": "…", "exerciseName": "Присед со штангой" } ] }
```

- `comments` — комментарии к упражнениям с этим роликом, по времени. `workoutDate` — `null`, пока тренировка
  не опубликована. По `workoutId` клиент открывает тренировку.
- `programs` — программы, в упражнениях которых ролик прикреплён: свои и действующих подопечных, по названию.
  `ownerId` — в чьём пространстве программа.

Ключи объектов производные (`video/{ownerId}/{id}.mp4` и `.jpg`), в ответах, логах и телеметрии их нет.

## Пределы

Настройки `sizylift.video.*` (`application.yaml`), не константы; пределы ролика — по видам,
`sizylift.video.limits.{set,technique}`. Видео техники длиннее: тренеру нужно время на разбор движения
(решение владельца 18.11.2026); две минуты 720p — около 40 МБ.

| Что | Значение | Отказ |
| --- | --- | --- |
| Видео подхода (`set`) | 60 с, 25 МБ; исходник из браузера — 300 МБ | 422 `video_too_long`, 422 `video_too_large` |
| Видео техники (`technique`) | 120 с, 50 МБ; исходник из браузера — 600 МБ | 422 `video_too_long`, 422 `video_too_large` |
| Кадр-превью | 200 КБ | 422 `video_too_large` |
| Квота пользователя | 300 МБ на `set`, 1 ГБ на `technique` | 409 `quota_exceeded` |
| Всё хранилище | 8 ГБ | 503 `storage_full` |

В квоту входят ролики и превью, включая незавершённые загрузки. Срока хранения нет. Перекодирования нет;
при завершении загрузки сервер проверяет содержимое без него (см. `complete`).

Квоты и общий предел не согласованы: 8 ГБ хватает примерно на 27 пользователей с полной квотой видео подходов.
Пока оповещений нет, сервер пишет в журнал предупреждение `WARN`, когда занятое переходит порог
`sizylift.video.fill-warnings` (70 % и 90 %); проверка — раз в `fill-check-interval`.

Ошибки — `{ "code": "…", "message": "…" }`. Остальные коды: 400 `invalid_video`, 422 `video_unsupported`,
403 `coach_required`
(видео техники загружает только аккаунт с включённым режимом тренера), 404 `not_found`, 409 `id_conflict`,
409 `upload_incomplete`.

## API `/api/v2/videos`

### `POST /api/v2/videos` — место под ролик

```json
{ "id": "…", "kind": "set", "sizeBytes": 12400000, "previewSizeBytes": 84000, "durationMs": 24000,
  "title": null, "exerciseId": "…", "exerciseName": "Присед со штангой" }
```

Ответ 200:

```json
{ "video": { "id": "…", "status": "pending", "…": "…" },
  "upload": { "videoUrl": "…", "videoContentType": "video/mp4",
              "previewUrl": "…", "previewContentType": "image/jpeg", "expiresAt": "…" } }
```

- Ссылки PUT живут 15 минут. В подпись входят `Content-Type` и точный размер тела: другой тип или размер
  хранилище отклоняет (403). Файл кладётся одним запросом PUT с заголовком `Content-Type` из ответа.
- Повтор с тем же `id`, видом и размерами до подтверждения загрузки возвращает новые ссылки и квоту второй
  раз не тратит — так приложение повторяет загрузку после обрыва. Для уже загруженного ролика `upload` —
  `null`. Чужой `id` или другие размеры — 409 `id_conflict`.

### `POST /api/v2/videos/{id}/complete` — загрузка завершена

Сервер проверяет, что оба объекта есть и их размер совпадает с заявленным, и переводит ролик в `ready`.
Ответ — ролик со ссылками. Объектов нет или размер другой — 409 `upload_incomplete`. Повтор для готового
ролика возвращает его же. Только владелец.

Затем — содержимое, запросами диапазонов, без чтения файла целиком:

- превью начинается с маркера JPEG;
- ролик — MP4: коробки верхнего уровня известных типов, в `moov` есть `mvhd` (индекс в начале или в конце
  файла, не больше `max-index-bytes`);
- длина из `mvhd` не больше `max-duration` + `duration-tolerance` (1 с: сжатие немного меняет длину).

Не прошёл — 422 `video_unsupported` или `video_too_long`; ролик удаляется сразу, снимается с комментариев
и программ (как при удалении), файлы уходят в очередь удаления. Повтор той же загрузки не поможет. У готового
ролика `durationMs` — настоящая длина из файла (не больше `max-duration`), а не заявленная.

Незавершённые загрузки старше суток ежедневная задача удаляет вместе с объектами.

### Загрузка из браузера

Сайт и PWA не сжимают видео: запрос места отличается, остальное — как у приложения.

```json
{ "id": "…", "kind": "set", "source": "browser", "sizeBytes": 148000000, "contentType": "video/quicktime",
  "durationMs": 24000, "title": null, "exerciseId": "…", "exerciseName": "Присед со штангой" }
```

- `sizeBytes` и `contentType` — исходного файла. Допустимые типы — `sizylift.video.browser.content-types`
  (MP4, QuickTime, WebM, Matroska, 3GP), иначе 422 `video_unsupported`. Исходник до 300 МБ у подхода
  и 600 МБ у техники (`limits.*.max-source-size-bytes`), иначе 422 `video_too_large`.
- `durationMs` браузер берёт из метаданных; не смог прочитать — не передаёт, длину проверит сервер.
- `previewSizeBytes` не нужен: в ответе одна ссылка PUT — на исходник (`videoUrl`, `videoContentType` — тип
  исходника), `previewUrl` пуст.
- В квоту до готовности входит место под результат (предел ролика своего вида и 200 КБ), не исходник;
  в общий предел хранилища —
  и исходник, пока он лежит.
- Бакет разрешает браузерам с адресов `sizylift.web.allowed-origins` класть и читать файлы (CORS); правило
  сервер ставит сам при запуске и повторяет, пока хранилище его не примет.

`complete` сверяет размер исходника и переводит ролик в `processing`. Обработчик (один, ролик за роликом,
опрос раз в `poll-interval`) скачивает исходник и перекодирует ffmpeg с пониженным приоритетом в один поток:
длинная сторона до 1280, H.264 high + AAC, `+faststart`, 2,5 Мбит/с, а если ролик не уложился в предел своего вида —
1,4 Мбит/с; поворот с телефона применяется. Превью — кадр на 0,5 с шириной 480 до 200 КБ. Затем ролик —
`ready` с настоящей длиной и размерами, исходник удаляется.

- Не видео, длиннее предела своего вида (+1 с) или не уложился в размер — ролик удаляется и снимается с комментариев
  и программ, как при отказе `complete`. Клиент узнаёт это по 404 на `GET`.
- Сбой хранилища или ffmpeg — ролик возвращается в очередь; после `max-attempts` (3) попыток удаляется так же.
  Ролик, брошенный упавшим сервером, подхватывается через удвоенный `timeout`.
- Владелец удалил ролик во время перекодирования — результат не сохраняется.

Метрики: `sizylift.video.processing{outcome}` (`ready`, `retry`, `deleted`, `rejected_*`),
`sizylift.video.processing.duration`.

### `GET /api/v2/videos/{id}` — сведения и ссылки на просмотр

Ссылки GET живут 10 минут; хранилище отвечает на запросы `Range` (206), ролик играет до полной загрузки.
У `pending` ссылок нет: клиент показывает «Видео загружается»; у `processing` — «Видео обрабатывается». Ролика нет, он чужой или недоступен — 404
(в том числе пока приложение не запросило место: комментарий со ссылкой на видео приходит раньше).

### `GET /api/v2/videos?kind=set|technique&cursor=&limit=` — свои ролики

Раздел «Видео»: ролики, загруженные самим пользователем, новые сначала. `limit` — 1…100, по умолчанию 30.

```json
{ "videos": [ { "…": "…", "previewUrl": "…", "videoUrl": null, "usage": { "…": "…" } } ],
  "nextCursor": null, "quota": { "usedBytes": 37200000, "limitBytes": 314572800 } }
```

В списке приходят только ссылки на превью; ролик открывается через `GET /api/v2/videos/{id}`. У подопечного
упражнение — `exerciseName`, дата — `usage.comments[0].workoutDate` (нет — `createdAt`), номер подхода —
`usage.comments[0].setNumber`, тренировка — `usage.comments[0].workoutId`. У тренера «где используется» —
`usage.programs`. Чужих роликов в списке нет: видео подопечных тренер смотрит в тренировках.

### `PATCH /api/v2/videos/{id}` — переименовать

`{ "title": "Присед: пауза внизу" }`. Только владелец. У видео техники название обязательно (пустое — 400
`invalid_video`), у видео подхода пустое снимает название. Ответ — ролик.

### `DELETE /api/v2/videos/{id}` — удалить

Только владелец. Ответ 200:

```json
{ "id": "…", "removedFrom": { "comments": [ … ], "programs": [ … ] } }
```

- Ролик снимается со всех комментариев и программ. Комментарий теряет `videoId` и `videoDurationMs`;
  комментарий без текста удаляется. У упражнений программ — своих, действующих и бывших подопечных —
  пропадает `techniqueVideoId`. Каждый затронутый агрегат получает новую ревизию и расходится по лентам
  (`upsert` или `delete`), как каскады сервера; push об этом не отправляется.
- `removedFrom` — то же, что `usage` до удаления: клиент спрашивает подтверждение по `usage` из списка или
  `GET`, а ответ удаления сообщает, откуда ролик убран на самом деле.
- Файлы удаляет фоновая задача (очередь `video_removal`, раз в минуту); при сбое хранилища повторяет.
- **Ролика на сервере нет** (приложение отменило загрузку раньше, чем запросило место): ролик снимается только
  с того, что вызывающий правит сам, — своих комментариев, своих программ и программ действующих подопечных.
  Ответ тот же, `removedFrom` — откуда снят. Ссылок нет и там — 404. Приложение так отменяет загрузку.
- Ежедневная задача снимает с комментариев ролики, которых на сервере нет дольше `orphan-ttl` (7 дней от
  создания комментария): отменённые загрузки, устройство потеряно, незавершённая загрузка удалена через сутки
  и приложение не вернулось. Без этого у тренера навсегда висит «Видео загружается».

## Видео упражнения

Тренер прикрепляет одно видео техники к упражнению целиком, и его видят все действующие подопечные там, где
встречается это упражнение: в программе, в тренировке, в карточке упражнения. Видео упражнения конкретной
программы (`techniqueVideoId`) остаётся и перекрывает видео упражнения — это решает клиент. Таблица
`exercise_video` (changeset `048-exercise-video`).

- `PUT /api/v2/videos/exercises/{exerciseId}` `{ "videoId": "…", "exerciseName": "Присед со штангой" }` —
  поставить или заменить. Только своё видео техники и включённый режим тренера: чужое — 404, видео подхода —
  400 `invalid_video`, без режима тренера — 403 `coach_required`. `exerciseName` — для «Где используется».
- `DELETE /api/v2/videos/exercises/{exerciseId}` — снять; не было — 404.
- `GET /api/v2/videos/exercises` — видео упражнений, которые видит вызывающий: свои (`own: true`) и
  действующего тренера. У одного упражнения своё главнее тренерского.

```json
{ "exercises": [ { "exerciseId": "…", "exerciseName": "Присед со штангой", "videoId": "…", "ownerId": "…",
                   "title": "Присед: вид сбоку", "status": "ready", "durationMs": 42000,
                   "previewUrl": "…", "urlExpiresAt": "…", "own": false } ] }
```

- `exerciseId` — в пространстве вызывающего. Каталожное упражнение у всех под одним id; упражнение из библиотеки
  тренера у подопечного — копия под производным id (`CoachExerciseCopies.copyId`, docs/coaching.md), поэтому
  подопечному отдаётся id копии. Своё упражнение подопечного тренер прикрепить не может.
- Удаление ролика снимает его и с упражнений (`removedFrom.exercises`); разрыв связи — и подопечный больше
  не видит видео упражнений тренера (404 на ролик).

## Доступ

| Видео | Видит | Загружает и удаляет |
| --- | --- | --- |
| `set` | владелец и его действующий тренер | владелец |
| `technique` | тренер-владелец и действующий подопечный, в чьей программе оно прикреплено или если оно — видео упражнения тренера | тренер-владелец |

После разрыва связи тренер получает 404 на видео подопечного, подопечный — на видео техники тренера;
`techniqueVideoId` в его программах остаётся, клиент скрывает кнопку по 404. Файлы при разрыве не
удаляются. Удаление аккаунта удаляет его ролики и файлы.

## Комментарий к упражнению и программа

- `workout_comment`: необязательные `workoutExerciseId`, `setNumber`, `videoId`, `videoDurationMs` —
  [coaching.md](coaching.md#комментарии).
- Программа: у упражнения необязательное `techniqueVideoId` — видео техники тренера. Хранится в
  `planned_exercise.technique_video_id`, копируется вместе с программой (назначение нескольким, приглашение
  с программой). Сервер не проверяет, что ролик существует: доступ решается при просмотре.
- Ни комментарий, ни программа не ждут загрузки ролика: в синхронизацию попадает только id.

## Хранилище

Garage v2.5.0 в отдельном контейнере, один узел (`deploy/garage/garage.toml`); сервер работает с ним только
через S3 API (AWS SDK). Смена хранилища — адрес и ключи в `sizylift.video.storage.*` и копирование бакета.
`endpoint` — адрес для сервера, `public-endpoint` — адрес в подписанных ссылках (в production —
`https://<MEDIA_DOMAIN>` через Caddy). Узел, ключ и закрытый бакет создаются при первом запуске контейнера
(`--single-node --default-bucket`).

Проверка Garage (ADR-0012, раздел 9) — `VideoApiTest` на том же образе в Testcontainers: подписанные PUT
с типом и размером в подписи, подписанные GET, `Range` → 206 с `Content-Range`, анонимный запрос → 403.
Квота бакета Garage (`garage bucket set-quotas`) работает, но общий предел считает сервер по таблице
`video` — так он не зависит от хранилища.

## Таблицы (changeset `036-video`)

- `video` — запись о ролике.
- `video_removal` — очередь удаления файлов (ролик, превью и исходник).
- Changeset `046-video-browser-upload`: статус `processing`, `source_content_type`, `source_size_bytes`,
  `processing_started_at`, `processing_attempts`.
- `workout_comment`: `workout_exercise_id`, `set_number`, `video_id`, `video_duration_ms`.
- `planned_exercise.technique_video_id`.

## Метрики

- `sizylift.video.stored.bytes` — занято роликами и превью; `sizylift.video.bucket.limit.bytes` — предел.
- `sizylift.video.bucket.used.ratio` — доля общего предела, занятая роликами и превью.
- `sizylift.video.removal.failures` — сбои удаления файлов из хранилища.
