# Рабочее место тренера: класс упражнения, %ПМ, «Входящие», задачи

Решения от 28.10.2026 по итогам UX-аудита веба (`sizy-lift-frontend/UX_DECISIONS.md`). Здесь — серверная часть
и контракты API, по которым веб и сервер делаются параллельно. Изменения схемы — changesets `019`–`021`.

Статус: в работе. Разделы 4–5 реализованы на сервере (changesets `020`, `021`).

## 1. Класс упражнения (`lift_class`) вместо `is_sbd`

Класс говорит, имеет ли смысл для упражнения расчётный ПМ и планирование в % от него.

| Значение | В интерфейсе | Что значит | ПМ и %ПМ |
| --- | --- | --- | --- |
| `sbd` | Соревновательное (SBD) | присед, жим лёжа, становая — соревновательные движения | да; кривые присед/жим/становая |
| `basic` | Базовое | многосуставное упражнение со свободным весом | да; общая кривая |
| `other` | Прочее | изоляция, тренажёры, блоки, свой вес, кардио, мобильность | нет |

**Схема (changeset `019-exercise-lift-class`):**

- `exercise.lift_class text NOT NULL DEFAULT 'other' CHECK (lift_class IN ('sbd','basic','other'))`;
- `CHECK (lift_class = 'other' OR result_type = 'weight_reps')` — SBD и «Базовое» только у «вес × повторения»
  (у упражнений с доп. весом % от ПМ без учёта собственного веса не имеет смысла);
- перенос данных: `is_sbd = true` → `sbd`; системные упражнения размечаются по списку ниже; свои упражнения
  пользователей без `is_sbd` → `other`;
- колонка `is_sbd` удаляется.

**Разметка системного каталога:**

- `sbd`: Присед со штангой, Жим штанги лёжа, Становая тяга классическая, Становая тяга сумо;
- `basic`: Фронтальный присед, Гоблет-присед, Болгарские выпады, Выпады с гантелями, Жим лёжа узким хватом,
  Жим штанги на наклонной скамье, Жим гантелей лёжа, Жим гантелей на наклонной скамье, Армейский жим,
  Жим гантелей сидя, Жим гантелей стоя, Румынская тяга, Тяга штанги в наклоне, Т-тяга, Тяга гантели в наклоне,
  Ягодичный мост со штангой;
- остальные — `other`.

**Совместимость с телефоном (переходный период).** Приложение пока знает только `isSbd`; его обновление —
отдельная задача (раздел 6), сервер не должен её ломать:

- в `ExercisePayloadV1` и в ответах (лента sync, `GET /api/v2/web/catalog`) остаётся `isSbd`, вычисляемый как
  `liftClass == "sbd"`; добавляется необязательное поле `liftClass`;
- при записи: есть `liftClass` → берётся он (`isSbd` игнорируется); нет `liftClass` → `isSbd = true` даёт `sbd`,
  `isSbd = false` оставляет прежний класс упражнения (если прежний был `sbd` — `other`), у нового — `other`;
- `liftClass` `sbd`/`basic` у упражнения не с `weight_reps` → `rejected: invalid`;
- когда приложение перейдёт на `liftClass`, `isSbd` убирается из контракта отдельной задачей.

## 2. %ПМ в плановом подходе

В подход программы (и плановой отдельной тренировки, если у неё та же модель подхода) добавляется необязательное
поле `targetPercentOneRmTenths` — процент от ПМ в десятых долях (`725` = 72,5 %), `1..1500`.

- В программе подопечного хранятся и вес, и процент: что тренер ввёл последним, то и пересчитало второе
  (это делает веб). Сервер вес по проценту не пересчитывает.
- В шаблоне (своя программа тренера) у подхода задан либо вес, либо процент — правило веба, сервер оба поля
  принимает.
- Телефон новое поле пока игнорирует и не показывает.

## 3. Кандидаты для расчётного ПМ

ПМ = максимум из расчётного ПМ по выполненным подходам за 30 дней и ПМ, введённого вручную за те же 30 дней.
Нет ни того, ни другого — ПМ нет, %ПМ выключается. Сервер ПМ **не хранит и не считает**: калькулятор один,
на TypeScript (общий у телефона и веба); сервер отдаёт подходы одним запросом.

### `GET /api/v2/web/max-candidates?ownerId=&from=YYYY-MM-DD`

Выполненные подходы упражнений классов `sbd`/`basic` с `workout_date >= from` (клиент передаёт свою дату
минус 30 дней), `weightGrams > 0`, `1 ≤ repetitions ≤ 12`. Права — как у остальных запросов `/api/v2/web`.

```json
{ "from": "2026-09-28",
  "sets": [ { "exerciseId": "…", "workoutId": "…", "workoutDate": "2026-10-20",
              "weightGrams": 140000, "repetitions": 5, "rpeTenths": 85 } ] }
```

Ручной ПМ — существующий `GET /api/v2/web/one-rep-maxes` (`achievedOn` фильтрует клиент).

## 4. «Входящие» тренера

Лента событий по всем подопечным. Пять типов, остальное (комментарии, рекорды) сюда не попадает:

| `kind` | Когда создаётся | `subjectId` / `subjectDate` |
| --- | --- | --- |
| `workout_completed` | подопечный опубликовал завершённую тренировку (первая публикация агрегата) | id тренировки / её дата |
| `workout_rescheduled` | подопечный создал или изменил перенос | id плановой тренировки / новая дата |
| `workout_missed` | ежедневная задача: плановая тренировка активной программы с датой (с учётом переноса) раньше вчерашнего дня, без завершённой тренировки по ней | id плановой тренировки / её дата |
| `program_ending` | ежедневная задача: до `end_date` активной программы 0–7 дней | id программы / `end_date` |
| `invite_accepted` | подопечный принял приглашение (создана связь) | — / — |

**Схема (changeset `020-coach-inbox`):** таблица `coach_event`: `id`, `link_id → coaching_link ON DELETE CASCADE`,
`kind` (CHECK по списку), `subject_id`, `subject_date`, `occurred_at`, `seen_at`, `dedup_key`
(`UNIQUE (link_id, dedup_key)`). Повторное событие с тем же ключом (новый перенос той же тренировки) обновляет
`occurred_at`/`subject_date` и сбрасывает `seen_at`; повторная публикация той же тренировки нового события не даёт.
События пишутся в той же транзакции, что и публикация. Ежедневная задача идемпотентна (по `dedup_key`).
Тренер видит события только по активной связи; после разрыва — ничего.

### `GET /api/v2/web/inbox?athleteId=&unseenOnly=false&limit=50&before=<occurredAt>`

```json
{ "unseenCount": 4,
  "events": [ { "id": "…", "athleteId": "…", "athleteName": "Иван Петров", "kind": "workout_completed",
                "subjectId": "…", "subjectDate": "2026-10-27", "title": "Присед, жим",
                "occurredAt": "…", "seenAt": null } ] }
```

`athleteId` — `user_account.id` подопечного (тот же, что `ownerId`). `title` — название тренировки или программы,
если есть. Порядок — `occurredAt` по убыванию.

### `POST /api/v2/web/inbox/seen`

Тело — хотя бы одно из полей: `{ "eventIds": ["…"] }`, `{ "athleteId": "…" }` (всё по подопечному),
`{ "subjectId": "…" }` (всё по объекту — веб шлёт, когда тренер открыл тренировку), `{ "all": true }`.
Отмечает подходящие непросмотренные события тренера. Ответ `204`.

### Список подопечных `GET /api/v2/web/athletes`

В `AthleteRow` добавляются:

```json
{ "unseen": { "workoutCompleted": 2, "workoutRescheduled": 0, "workoutMissed": 1, "programEnding": 0,
              "inviteAccepted": 0 },
  "oldestUnseenAt": "…",
  "openTasks": 3, "overdueTasks": 1 }
```

Порядок: сначала подопечные с непросмотренными событиями — по `oldestUnseenAt` по возрастанию (кто ждёт
дольше), затем остальные — по `activityAt` по убыванию. `hasNew` и `POST /{linkId}/seen` остаются до перехода
веба, затем удаляются.

### Решения реализации

- Конец программы — максимальный `end_date` её недель; «активная» — `program.status = 'active'`.
- `occurredAt` — время записи на сервере (для задачи — время запуска), не время тренировки.
- `dedup_key`: `workout_completed:<id>`, `workout_rescheduled:<плановая>`, `workout_missed:<плановая>:<дата>`,
  `program_ending:<программа>:<end_date>`, `invite_accepted`. Перенесённая и снова пропущенная тренировка или
  продлённая программа дают новое событие.
- Удаление тренировки удаляет её `workout_completed` (и просмотренное: объекта больше нет); повторная публикация
  после удаления — снова «первая». Отмена переноса удаляет `workout_rescheduled`. Завершённая тренировка
  с `plannedWorkoutId` удаляет `workout_missed` по этой плановой.
- События пишет только запись самого подопечного (v1 и v2, через `FeedFanout`); записи сервера (каскады,
  копии упражнений) и тренера событий не дают.
- Ежедневная задача: `sizylift.coach-workspace.daily-cron` в зоне `sizylift.coach-workspace.zone`
  (`Europe/Moscow`). Пропущена — дата раньше вчерашнего дня, но не старше 14 дней
  (`CoachInboxDailyJob.MISSED_LOOKBACK_DAYS`) и не раньше дня создания связи. При нескольких экземплярах
  запуск берёт `pg_try_advisory_xact_lock`, второй пропускает; повтор идемпотентен по `dedup_key`.
- Лента: `before` строгий; необязательный `beforeId` разводит события с одинаковым `occurredAt`
  (их создаёт один запуск задачи). `limit` 1–200. `unseenCount` учитывает `athleteId`.
- `seen`: заданные поля складываются через «и»; `all: true` — без ограничений; пустой запрос → 400.
- Задачи: «просрочена» — открыта и `dueOn` раньше сегодняшнего дня в той же зоне. `status` вне списка → 400.
  Повторный `done: true` не меняет `doneAt`, `done: false` его сбрасывает.

## 5. Задачи тренера

Задачи тренер заводит **только вручную**, по конкретному подопечному. Видит только тренер. Сортировку подопечных
не меняют.

**Схема (changeset `021-coach-task`):** таблица `coach_task`: `id`, `link_id → coaching_link ON DELETE CASCADE`,
`text` (1–500 символов), `due_on date`, `done_at`, `created_at`, `updated_at`. После разрыва связи задачи
не видны.

### API `/api/v2/web/tasks`

- `GET /api/v2/web/tasks?athleteId=&status=open|done|all` (по умолчанию `open`) →
  `{ "tasks": [ { "id", "athleteId", "athleteName", "text", "dueOn", "doneAt", "createdAt", "updatedAt" } ] }`;
  порядок: открытые — по `dueOn` (без срока — в конце), затем по `createdAt`; сделанные — по `doneAt` по убыванию;
- `POST /api/v2/web/tasks` `{ "athleteId", "text", "dueOn"? }` → задача, `201`;
- `PATCH /api/v2/web/tasks/{id}` `{ "text"?, "dueOn"?, "done"? }` → задача (`dueOn: null` снимает срок);
- `DELETE /api/v2/web/tasks/{id}` → `204`.

Чужая задача или подопечный без активной связи → `404`.
