# Администрирование Sizy

Первая версия: только чтение, владелец с ролью `sizy-admin`, адрес сайта `/admin`.
Мобильное приложение не меняется.

## Вход и границы доступа

Отдельный public-клиент `sizy-admin` использует Authorization Code + PKCE S256.
Его browser flow `sizy-admin-browser` требует пароль и OTP, без обхода через SSO-cookie.
Новый администратор сначала настраивает TOTP. У обычного сайта остаётся `sizylift-web`.
Backend требует одновременно `azp=sizy-admin` и роль `realm_access.roles: sizy-admin`.
Роль не выдаётся при регистрации и не связана с `coach_enabled`.
Токены остаются в памяти браузера. Все административные ответы имеют `Cache-Control: no-store`.

Уже выданный JWT остаётся действителен до истечения срока (5 минут + допуск времени).
Это относится и к отзыву административной роли; немедленный отзыв не добавлялся.

## Пользователи

Источник регистраций — Keycloak, включая незавершённые регистрации и людей без аккаунта Sizy.
Каталог читается отдельным сервисным клиентом только с `realm-management/query-users`
и `realm-management/view-users`. Клиент удаления аккаунтов не используется.
Секрет никогда не отправляется браузеру.

Короткий снимок каталога хранится в памяти 30 секунд. Все страницы Keycloak загружаются
перед фильтрацией и пагинацией. Защитный предел — 10 000 пользователей; при его превышении
каталог возвращает 503, а не частичный список. При росте потребуется индексированный каталог.
Sizy присоединяется по `issuer + subject`, предметные данные — по `user_account.id`.
Контактные данные для админки берутся из Keycloak, а не из потенциально старой копии email.

`created_at` — первое создание аккаунта Sizy. Новое поле `last_seen_at` обновляется
для аккаунта вызывающего при обращении к функциям API с точностью до минуты.
Старую активность не восстанавливаем. Офлайн-использование и правки тренера за подопечного
не являются активностью подопечного. Административные чтения не создают аккаунты
просматриваемых пользователей. Данные здоровья, тексты тренировок и переписка не возвращаются.

## Метрики и контейнеры

Backend выполняет только фиксированные PromQL-запросы во внутреннем Prometheus.
Разрешены периоды `15m`, `1h`, `6h`, `24h`; обычный ответ — около 120 точек,
`detail=true` — до 601 точки с включёнными границами. Шаг не меньше 30 секунд.
Режимы имеют раздельный кеш 20 секунд и ограниченные таймауты. CPU и HTTP-rate
по-прежнему усредняются за 5 минут; детализация не меняет исходную частоту сбора.
Отсутствующие данные не заменяются успешным статусом. Время получения ответа и время
последнего исходного измерения различаются; метрики старше двух минут считаются несвежими.

`node-exporter` читает корневую файловую систему хоста через read-only mount.
SSD означает свободное место, RAM учитывает `MemAvailable`, swap показывается отдельно.
Диск: предупреждение от 80% занятости, критическое состояние от 90%.
История ограничена фактическим сроком хранения Prometheus; выбор 7 дней не создаёт прошлые данные.

Контейнеры читаются из Docker по точной метке текущего Compose-проекта (по умолчанию `sizylift`), включая остановленные.
Показываются состояние контейнера, Docker healthcheck и число перезапусков.
`running` не равнозначно исправному сервису. Если healthcheck отсутствует, показывается
«Проверка не настроена». Эти проверки выполняются внутри сервера и не заменяют внешний uptime monitor.

Шлюз `admin-runtime` имеет Docker socket только в отдельном контейнере, в изолированной
внутренней сети с backend. Он не публикует порт на хост и не предоставляет произвольный
Docker API. Разрешены только список, выбранные поля состояния и ограниченные stdout/stderr.
Mount сокета `:ro` сам по себе не ограничивает методы Docker API: ограничение задаёт код шлюза.
Компрометация самого шлюза остаётся риском привилегированного сокета; не подключайте
к его сети посторонние сервисы.

Логи: последние 1–500 строк, максимум 1 MiB, периоды 1 час / 24 часа / 7 дней, без follow.
Поиск выполняется по загруженным строкам. Доступность истории зависит от log driver и ротации Docker;
при unsupported driver возвращается недоступность. Известные форматы токенов, паролей и
authorization/cookie маскируются, но маскирование не заменяет запрет писать секреты в исходные логи.
Логи отображаются текстом, без выполнения HTML, и не сохраняются приложением в базе.

## Контракт

Все маршруты ниже начинаются с `/api/v2/admin` и доступны только после административного входа:

- `GET /access` — проверка доступа без обращения к источникам.
- `GET /overview` — зарегистрировано, новые за 7 дней, есть аккаунт Sizy.
- `GET /users?search=&state=all&coach=all&sort=registered&page=0&size=25`.
  Состояния: `active|pending|disabled|all`; тренер: `true|false|all`;
  сортировка: `registered|activity|name`; размер страницы 1–100.
- `GET /users/{id}` — карточка. `id` — идентификатор каталога Keycloak,
  `accountId` — UUID аккаунта Sizy либо null.
- `GET /metrics?period=1h&detail=false` — ряды `{id, unit, state, points:[{time,value}]}`.
  `time` — Unix seconds; нет данных — пустой ряд с явным состоянием.
- `GET /containers` — состояние и метка времени снимка.
- `GET /containers/{64-character-id}/logs?period=1h&limit=200` — ограниченный текстовый журнал.

Без токена — 401, без роли или при другом клиенте — 403, неверные параметры — 400.
Недоступный каталог — 503; недоступность метрик и контейнеров обозначается в ответе,
чтобы остальные части панели продолжали работать.

## Настройка существующего production

Production в рамках разработки не изменяется. Перед применением откройте PR frontend и backend.
Файл realm импортируется только в **новый** realm; существующий realm перезапуском не обновляется.
Не удаляйте тома и не переимпортируйте realm поверх рабочих пользователей.

1. В Keycloak создайте realm role `sizy-admin`, назначьте только своему личному пользователю.
2. Создайте browser flow `sizy-admin-browser` (Basic flow). Добавьте
   `Username Password Form` и `OTP Form`, обе REQUIRED в таком порядке. Не добавляйте Cookie
   или альтернативные ветки, пропускающие OTP.
3. Создайте OIDC public client `sizy-admin`: Standard flow включён,
   implicit/direct grants/service accounts выключены, PKCE S256.
   Redirect URI: `https://<WEB_DOMAIN>/auth/admin/callback` и `/auth/admin/silent`;
   Home URL — `https://<WEB_DOMAIN>/`; Web Origin — точный адрес сайта;
   post-logout redirect — главная сайта.
   В Authentication flow overrides → Browser выберите `sizy-admin-browser`.
4. У клиента выключите Full scope allowed, добавьте в scope mapping только `sizy-admin`.
   Добавьте audience mapper `sizylift-api` и realm-role mapper `realm_access.roles`
   (multivalued JSON String), оба только в access token. Точные представления —
   в `keycloak/realm-sizylift.json`, клиент `sizy-admin`.
5. У личного пользователя добавьте required action Configure OTP.
   Создайте confidential client `sizy-admin-read`: Service accounts включено,
   браузерные потоки/direct grants выключены. Его service account выдайте только
   `realm-management/query-users` и `realm-management/view-users`.
6. В `deploy/.env` задайте `KEYCLOAK_ADMIN_READ_CLIENT_ID` и
   `KEYCLOAK_ADMIN_READ_CLIENT_SECRET`. Не публикуйте секрет.
   Без них остальной стек запускается, но каталог админки возвращает 503.
7. Обновите backend, соберите его штатной командой `./gradlew build`, затем обновите frontend.
   Запустите штатный production Compose с пересборкой: он добавит node-exporter,
   admin-runtime и конфигурацию Prometheus. Миграция 025 добавляется автоматически.
8. Проверьте: обычному пользователю административный API отвечает 403;
   пароль без OTP не завершает административный вход; видны все ожидаемые пользователи;
   метрики свежие; доступны логи каждого контейнера проекта.

Образы добавленных сборщиков и шлюза не открывают публичные порты. SSH-доступ к Grafana
и технической консоли Keycloak сохраняется для обслуживания.

## Переименование административных клиентов

Для новой админки используются `sizy-admin` и `sizy-admin-read`. Если клиенты уже
созданы с прежними именами `sizylift-admin` / `sizylift-admin-read`, измените их
Client ID в Keycloak и значение `KEYCLOAK_ADMIN_READ_CLIENT_ID` в серверном `.env`.
Обновите backend и frontend вместе с настройками клиентов. Роль остаётся `sizy-admin`.
Рабочий realm `sizylift` и существующие клиенты сайта/телефона сохраняют свои идентификаторы.

## Локальная проверка

Frontend: `npm run verify`; API/реальный PostgreSQL/Keycloak: `./gradlew build`;
шлюз: `python -m unittest discover -s deploy/admin-runtime -v`.
Для локальной админки настройте те же Keycloak client/flow и service account;
адреса источников можно задать через `SIZYLIFT_ADMIN_KEYCLOAK_URL`,
`SIZYLIFT_ADMIN_KEYCLOAK_CLIENT_ID`, `SIZYLIFT_ADMIN_KEYCLOAK_CLIENT_SECRET`,
`SIZYLIFT_ADMIN_PROMETHEUS_URL`, `SIZYLIFT_ADMIN_RUNTIME_URL`.

В production срок хранения телеметрии — 24 часа; недельный период API не принимает.
Журналы контейнеров ограничены ротацией Docker (3 файла по 10 МиБ), поэтому могут
содержать меньше суток. Параметры и обновление — [observability.md](observability.md#хранение-в-production).
