# Синхронизация v2

Контракт и поведение записи `POST /api/v2/sync/push` и ленты `GET /api/v2/sync/changes`. Решения и обоснования — в
[ADR-0007](adr/0007-two-way-sync-and-coaching.md); публикация v1 осталась и описана в
[publication.md](publication.md).

Статус: реализованы запись (этап 1), лента изменений (этап 2), права тренера и фан-аут тренеру
(этап 3), переносы и комментарии (этап 4) — [coaching.md](coaching.md).

## Запись: `POST /api/v2/sync/push`

До 100 элементов в пачке, как в v1. Каждый элемент обрабатывается в своей транзакции; ошибка одного
не влияет на остальные.

```json
{ "items": [ { "type": "program", "id": "…", "ownerId": null,
               "baseRevision": 41, "changedAt": "2026-10-23T09:14:02Z",
               "clientId": "device-7f3a", "clientVersion": 18,
               "schemaVersion": 1, "deleted": false, "payload": { … } } ] }
```

| Поле | Смысл |
| --- | --- |
| `type`, `id`, `schemaVersion`, `deleted`, `payload` | как в v1: те же типы агрегатов и те же payload v1, плюс `workout_reschedule` и `workout_comment` ([coaching.md](coaching.md)) |
| `ownerId` | только при записи чужих данных: тренер пишет программу подопечного. Права — `AccessPolicy` ([coaching.md](coaching.md)), без права — `rejected: forbidden` |
| `baseRevision` | ревизия, от которой клиент правил; `0` — новый агрегат |
| `changedAt` | время последней локальной правки по часам клиента |
| `clientId`, `clientVersion` | устройство или веб-сессия и её счётчик правок агрегата; делает повтор идемпотентным |

Ответ — по элементу: `{type, id, clientVersion, status, revision, error, payloadRewritten}`.
`payloadRewritten: true` — сервер сохранил payload не таким, как прислан (ссылки программы тренера
переписаны на копии упражнений у подопечного, [coaching.md](coaching.md)); клиент берёт агрегат из
ленты, даже если ревизия совпадает с ответом.

| `status` | Смысл |
| --- | --- |
| `accepted` | правка записана, `revision` — новая ревизия агрегата |
| `superseded` | правка проиграла более поздней и записана только в журнал конфликтов; `revision` — текущая серверная, клиент перечитает агрегат |
| `stale` | повтор уже обработанной правки этого клиента (`clientVersion` не больше последней обработанной от этого `clientId`, даже если после неё агрегат писал другой клиент); `revision` — текущая |
| `rejected` | не принят, `error`: `unsupported_type`, `unsupported_schema`, `invalid_payload`, `id_conflict`, `forbidden` |

### Порядок обработки элемента

1. Проверки: тип, версия схемы, payload (Bean Validation).
2. Разделяемая блокировка аккаунта владельца данных: связь тренера не меняется до коммита записи.
   Пишет ли вызывающий вообще за этого владельца (сам владелец или активный тренер для программ), иначе
   `forbidden`.
3. Блокировка строки `published_aggregate` (`INSERT … ON CONFLICT DO NOTHING` + `SELECT … FOR UPDATE`).
   Право на конкретный агрегат: у агрегата один писатель (`author_user_id`), иначе `forbidden`.
4. Повтор: `clientVersion` не больше последней обработанной правки этого `clientId` по агрегату
   (`aggregate_client_version`) → `stale`. Иначе версия клиента запоминается — и при записи, и при
   проигрыше, чтобы повтор проигравшей правки не дублировал журнал.
5. `changedAt` обрезается до `min(changedAt, время сервера)`, с точностью до микросекунды.
6. `baseRevision` равна текущей ревизии — запись без конфликта.
7. Иначе конфликт. `baseRevision` больше текущей корректный клиент прислать не может (бывает после
   восстановления базы из бэкапа): это тоже конфликт, и он считается метрикой
   `sizylift.sync.push.base.ahead`. побеждает более поздний `changedAt`, при равенстве — сохранённая версия.
   Выигравшая входящая правка → `accepted`, сохранённая версия уходит в журнал.
   Проигравшая → `superseded`, она уходит в журнал.
8. Запись данных (замена агрегата целиком, под владельцем), новая ревизия из `aggregate_revision_seq`,
   `changed_at`, `source_client_id`, `source_version`. Автора запись не меняет: его ставит только
   создание агрегата не владельцем (программа тренера) и сбрасывает разрыв связи.
9. Каскады: удаление тренировки удаляет её комментарии, запись программы снимает устаревшие переносы
   (tombstone с новой ревизией).
10. Фан-аут в ленты получателей последним шагом, включая удалённые каскадом агрегаты.

Удаление — запись с `deleted = true` по тем же правилам: tombstone с ревизией, конкурирует с правкой
по `changedAt`.

### Журнал конфликтов

`aggregate_conflict(user_id, type, aggregate_id, lost_payload, lost_changed_at, lost_client_id,
winner_revision, created_at)`, хранится 30 дней (`ConflictRetention`, ежедневно ночью). Данные пишутся
только сервером; в API журнала пока нет.

`lost_payload` — содержимое проигравшей версии в формате payload v1: у входящей правки — присланный
payload, у вытесненной сохранённой — собранный из таблиц (`AggregateReader`) до замены. Пуст только у
tombstone.

## Лента: `GET /api/v2/sync/changes?after=<seq>&limit=<n>`

Персональная лента получателя: какие агрегаты изменились, сразу с текущим payload. `after` — курсор
(по умолчанию `0`), `limit` — от 1 до 500 (по умолчанию 100). Кроме числа записей страница ограничена
объёмом payload, 1 МБ; первая запись отдаётся всегда.

```json
{ "changes": [ { "seq": 42, "ownerId": "…", "type": "program", "id": "…", "revision": 1017,
                 "kind": "upsert", "changedAt": "2026-10-23T09:14:02Z",
                 "schemaVersion": 1, "payload": { … } } ],
  "nextCursor": 42, "hasMore": false }
```

| Поле | Смысл |
| --- | --- |
| `seq` | позиция в ленте получателя, растёт |
| `ownerId` | чьи данные: сам получатель или его подопечный |
| `revision` | серверная ревизия агрегата; клиент отправит её как `baseRevision` |
| `kind` | `upsert` — payload v1 в том же формате, что при публикации; `delete` — агрегат удалён, payload нет; `revoke` — доступ потерян (разрыв связи, отзыв разрешения на травмы), копию удалить |
| `changedAt` | время последней правки агрегата |
| `authorId` | кто пишет агрегат, если не владелец (программа или комментарий тренера); иначе `null` |
| `nextCursor` | передать как `after` следующего запроса; без новых записей равен `after` |
| `hasMore` | за страницей есть ещё записи |

### Как устроено

- `sync_feed` — индекс последних изменений: одна строка на агрегат для получателя
  (`UNIQUE (user_id, owner_user_id, type, aggregate_id)`). Новая запись агрегата переносит строку на
  новый `seq`, поэтому лента не растёт бесконечно, а клиент после долгого офлайна получает только
  последнее состояние каждого агрегата.
- Позиция выдаётся под блокировкой строки `sync_cursor` получателя (`UPDATE … SET last_seq =
  last_seq + 1 … RETURNING`), последним шагом транзакции записи. Записи в одну ленту сериализуются,
  порядок `seq` совпадает с порядком коммитов, и читатель с курсором ничего не пропускает. Курсоры
  нескольких получателей блокируются в порядке `user_id`.
- В ленту попадают записи и через sync v2, и через публикацию v1 (`AggregateChangeListener`).
  Получатели — владелец и активный тренер, если видит этот тип (`AccessPolicy.recipients`).
- Новая связь засевает ленту тренера всеми видимыми агрегатами подопечного, разрешение на травмы —
  травмами; разрыв и отзыв разрешения переводят записи тренера в `revoke` с новыми позициями.
- Каждая запись о чужих данных при чтении перепроверяется `AccessPolicy.canRead`: без права вместо
  данных отдаётся `revoke`.
- Страница ленты и payload читаются из одного снимка (`REPEATABLE READ`, только чтение): ревизия
  записи ленты соответствует отданным данным.
- Миграция засеяла ленты владельцев всеми уже опубликованными агрегатами, так что первое чтение с
  `after=0` возвращает всё.

## Совместимость с публикацией v1

`POST /api/v1/publication/batch` работает как раньше: версия агрегата — счётчик телефона, не новее
сохранённой → `stale`. Дополнительно, если агрегат последним записан через sync v2, побеждает правка
с более поздним `updatedAt` корня payload (у tombstone — время получения). Проигравшая v1-запись
получает `stale` (в v1 нет `superseded`) и попадает в журнал; выигравшая вытесняет версию v2, тоже
с записью в журнал. Любая запись v1 тоже получает серверную ревизию и `changed_at`.

**Чужой автор.** v1 не знает авторов, поэтому публикация v1 отклоняет (`rejected: forbidden`) запись
агрегата, у которого `author_user_id` задан и не равен владельцу (программа тренера). Иначе старое
приложение подопечного опубликует свою локальную копию программы тренера и тихо заберёт её себе.

## Что должен соблюдать клиент

- Сохранять `revision` из ответа и отправлять её как `baseRevision` при следующей правке.
- Ставить `clientVersion` из собственного возрастающего счётчика правок агрегата.
- На `superseded` перечитать агрегат из ленты и показать пользователю, что правка заменена.
- Ленту применять локально, не поднимая локальную версию и не ставя агрегат в outbox: иначе
  полученное вернётся обратно на сервер.
- Пропускать собственное эхо: запись ленты с `revision`, равной уже сохранённой, — ничего не делать.
  Исключение — ответ с `payloadRewritten: true`: эту ревизию применить из ленты.
- Сдвигать курсор (`nextCursor`) только после локального коммита страницы.
- Полная пересинхронизация — чтение с `after=0`.

## Метрики

- `sizylift.sync.push.items{type,status}` — итог по элементу;
- `sizylift.sync.conflicts{type,outcome}` — конфликты: `accepted` (входящая выиграла), `superseded`
  (входящая проиграла); считаются и для проигрышей v1;
- `sizylift.sync.push.base.ahead{type}` — `baseRevision` новее серверной ревизии (признак
  восстановления базы или ошибки клиента);
- `sizylift.sync.changes.page.size` — записей на странице ленты;
- `sizylift.sync.push` — наблюдение (таймер и span `sync push`) на пачку.
